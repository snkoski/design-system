# How Rich text works

Rich text is a text field where formatting shows as you type: bold, italic, underline, strikethrough, inline code, links, quotes, lists, and code blocks. Its value is Markdown, the plain-text format where `**bold**` means bold and `- ` starts a list item. You see formatting; the form gets Markdown.

It's built from four outside pieces. You'll meet each one below:

- **ProseMirror** is the editing engine. It keeps the content as a tree of nodes, draws it into a `contenteditable` element (one the browser lets you type into), and turns everything you do into changes to that tree.
- **Tiptap** is a friendlier layer over ProseMirror, with React bindings. Its features come as **extensions**: packages that each add a kind of content, commands, keyboard shortcuts, or behavior. Bold is one extension, and so are lists.
- **marked** is a Markdown reader. Tiptap's `@tiptap/markdown` package uses it to turn Markdown into the editor's tree, and writes the tree back out as Markdown.
- **Base UI** provides everything around the editing: the label and its links, the toolbar, the toggle buttons, the tooltips, and the link popover.

## 1. What the editor holds

The editor doesn't hold Markdown, and it doesn't hold HTML. It holds a **document**: a tree of nodes. Block nodes are lines and containers (`doc`, `paragraph`, `blockquote`, `bulletList`, `listItem`, `codeBlock`). Inside them are text nodes. Formatting on text is a **mark**: a label on a run of text, such as `bold`, `italic`, or `link` (which also carries its address).

So `Hi **Ada**` is held as:

```text
doc
  paragraph
    text "Hi "
    text "Ada"   marks: bold
```

And a list item is a paragraph inside a `listItem` inside a `bulletList`. Marks are flat, not nested: bold italic text is one text node with two marks.

The document and the selection together are the editor's **state**. Nothing changes the state directly. Every change, whether a typed letter, a toolbar button, or loading a new value, is a **transaction**: a description of the change (insert this, delete that, add this mark there) that ProseMirror applies to the old state to make a new one. The undo history is a list of transactions, which is how undo knows what to take back. Section 4 listens for transactions to keep the toolbar up to date.

### Positions

A selection is two numbers, `from` and `to`. ProseMirror counts through the document: each character is one position, and so is each step into or out of a node. In `Hi **Ada**`, position 0 is before the paragraph, 1 is just inside it, before the `H`, and the text runs to 7, after `Ada`. Leaving the paragraph makes 8, which is the end if that's all there is. With nothing selected, `from` and `to` are the same: that's the caret.

This is an editor with the field's real extensions. Click in it, select some text, or press a button to see the positions, the path from the document down to the caret, and which formats are on there. The buttons run the real toolbar's commands (section 4).

## 3. Typing

When you type, the browser changes the `contenteditable` element, and ProseMirror notices. It reads what changed, turns it into a transaction, and redraws only the parts of the page that changed. React doesn't redraw the text: the component's render never touches the document.

### Typed Markdown becomes formatting

Typing Markdown formats it straight away. That's Tiptap's **input rules**, which come with each StarterKit extension. An input rule is a regular expression (a text pattern) checked against the text just before the caret each time you type a character. When it matches, its handler changes the document.

Say you've typed `A **bold*` and type the last `*`. The text before the caret is now `A **bold**`, and Bold's rule matches it. In `@tiptap/extension-bold`, the pattern is `/(?:^|\s)(\*\*(?!\s+\*\*)((?:[^*]+))\*\*(?!\s+\*\*))$/`: a start of line or a space, then two stars, some text with no stars, and two stars, right at the caret. The handler deletes the four stars, adds the `bold` mark to "bold", and removes the "stored mark", so the next letter you type isn't bold. Press Backspace straight away and the rule is undone: the stars come back.

Tiptap calls the editor's `onUpdate` after every transaction that changes the document (not when only the caret moves). `RichText` writes the document out with `toMarkdown()`, keeps that in state for the form, and calls `onValueChange` if it's different from what it last reported. `toMarkdown()` fixes two things about Tiptap's own `getMarkdown()`. A field with no text at all is always `""`, even when it holds an empty list item or quote. ### Running a tool

Pressing a button runs `tool.run(editor.chain().focus()).run()`. For Bold, that's `editor.chain().focus().toggleBold().run()`:

1. `focus()` puts focus back in the field. With a mouse, focus never left: the button cancels `mousedown`, which is what would move focus to it. With the keyboard, focus is on the button, and this sends you back to the text so you can carry on typing.
2. `toggleBold()` looks at the selection. If all of it is bold, it takes bold off; otherwise it puts bold on all of it. With nothing selected, it sets a **stored mark** instead: nothing changes yet, but the next letters you type are bold.
3. `run()` sends the transaction.

The block tools work on whole lines. `toggleBlockquote()` wraps every line in the selection in a `blockquote`, or lifts them out of one. The list tools do the same with a list and its items, and `toggleCodeBlock()` turns the lines into a code block, or back into paragraphs.

## 5. Links

The link button, or Mod-K, sets `linkOpen`, which opens a Base UI popover under the button. The popover moves focus into it when it opens and back to the field when it closes. When nothing is selected, it asks for the link's text as well as its address.

When focus moves into the popover, the browser stops showing the field's selection, so you can't see which text the link will go on. `MarkedSelection` draws it instead, with a ProseMirror **decoration**: styling drawn over the document without changing it. ## 6. Markdown in and out

### Reading Markdown

Loading Markdown (the starting value, a new `value`, or a paste) goes through `editor.markdown.parse()` in three stages:

1. **Tokens.** marked's **lexer** splits the text into tokens: a `paragraph` token, a `list` token, and inside them inline tokens such as `text`, `strong`, `em`, and `link`. Each token records the text it matched (`raw`).
2. **Nodes.** Each token type is handed to the extension that registered for it. Its `parseMarkdown` returns the matching nodes and marks: `strong` becomes text with a `bold` mark.
3. **The document.** ProseMirror builds a document from those nodes. Its **schema**, the rules for which nodes can go where, which StarterKit and the other extensions define, keeps anything that doesn't fit out.

So `Hi __Ada__` becomes a `paragraph` token holding `text "Hi "` and `strong "__Ada__"`, then a paragraph holding "Hi " and "Ada" with a bold mark.

### Writing Markdown

`getMarkdown()` goes the other way. It walks the document, and each node and mark writes itself with its `renderMarkdown`: bold as `**`, italic as `*`, and list items with `- `. There's one way to write each thing, so Markdown that went in written another way comes out rewritten: `__bold__` comes back as `**bold**`, and `* item` as `- item`. The text and formatting are the same; only the spelling changes.

### What this field changes

**Underline** isn't in standard Markdown. This field stores it as the HTML tag `<u>`, which Markdown allows and which renders anywhere HTML does. `UnderlineTag` teaches marked to read it and Tiptap to write it:

### Pasting

When you paste, the browser hands over the clipboard as plain text, HTML, or both. ProseMirror decides what to use:

1. Into a code block, the plain text goes in exactly as it is.
2. With HTML on the clipboard (copied from a web page or a document), it reads the HTML through the schema, keeping only the formats this field has.
3. With only plain text, or when you paste as plain text with Cmd+Shift+V, it calls `clipboardTextParser`. `PasteMarkdown` reads the text as Markdown there, so text copied from somewhere that stores Markdown keeps its look. ## 7. The value

The field works both ways React fields do: uncontrolled, where you give it a `defaultValue` and it keeps its own content, and controlled, where you pass `value` and update it from `onValueChange`. In both cases the editor's document is the real content, and Markdown is how it goes in and out.

- **For forms**, `RichText` keeps the latest Markdown in state and renders it in a hidden `<input>` with the field's `name`, so a form submits the Markdown.
- **From the start**, a layout effect writes the field's own Markdown into that state, so a `defaultValue` of `__b__` submits `**b**`, as `onValueChange` would report it.
- **A form reset** puts an uncontrolled field back to its `defaultValue`, as it does a native field. A reset doesn't change a hidden input, so the component listens for the form's `reset` event and reloads the editor itself.

### Controlled, without moving the caret

Replacing the editor's content moves the caret, so the field must not do it every time `value` changes. It keeps `lastReported`, the last Markdown it sent to `onValueChange` or was given. Say a parent stores the value in state:

1. You type "a". The field reports `"a"`, and sets `lastReported` to `"a"`.
2. The parent's state changes, and it passes `value="a"` back.
3. The field sees that `value` is `lastReported`. It's what the editor already holds, so it does nothing, and the caret stays where you are.

When the parent passes something new, such as `""` after sending a message, it's different from `lastReported`. The field replaces the content with `setContent`, without reporting it back (`emitUpdate: false`) and without an undo step (`addToHistory: false`), so undo can't bring back a sent message. It puts the caret at the end.

When `disabled` or `readOnly` changes, an effect calls `editor.setEditable()`, so the editor isn't rebuilt.

## 8. Accessibility

### Its name, description, and error

Base UI's `Field` links a label, description, and error to a control, but it expects an `<input>`. `Field.Control` has a `render` function, which hands over the linking attributes (`aria-labelledby` and `aria-describedby`). `RichText` adds the field's own (`role="textbox"`, `aria-multiline`, `aria-invalid`, `aria-required`, `aria-readonly`, `aria-disabled`, `aria-placeholder`, and `id`) and passes them to `EditorSurface`:

<Code file="experiments/RichText/RichText.tsx" name="EditorSurface" />

ProseMirror draws the editable `div` itself, so React can't set its attributes. Instead, the editor's `attributes` option is a function that returns whatever `attributesRef` holds, and ProseMirror calls it each time it draws. When the attributes change, `EditorSurface` stores the new ones and calls `updateState`, which makes ProseMirror draw, and read them, straight away.

The label is a `span`, not a `<label>`, because a `<label>` only works for form elements, not a `div`. Base UI's label focuses the field by its `id` when you click it. A screen reader gets the name from `aria-labelledby`.

### The keyboard

- **The toolbar is one Tab stop.** Tab reaches it before the field, on its first button. The arrow keys move between buttons, wrapping at the ends, and Tab moves on to the field. Base UI's `Toolbar` handles this (it's called a **roving tab stop**). The toolbar is named "Formatting", its groups are named "Text style", "Insert", and "Blocks", and `aria-controls` says which field it formats.
- **Shortcuts work in the field**, so you don't have to go back to the toolbar. Each button's `aria-keyshortcuts` tells screen readers its shortcut, and its tooltip shows it.
- **Tab leaves the field**, even in a list (`ListItemNoTab`, section 3). Enter adds a line.
- **Read-only** has no toolbar, since none of it could be used, and its absence shows that the field can't be changed. It stays in the tab order (`tabindex="0"`), so you can reach, read, and copy its text and follow its links. It's still submitted.
- **Disabled** is skipped by Tab, toolbar and field alike, and isn't submitted.

`rich-text.css` (in full below) handles the visual side:

- **Focus** inside the editable area draws the focus outline round the whole box, toolbar included, with `:has(.rich-text__editor:focus-visible)`. Toolbar buttons draw their own.
- **A pressed button** has a fill, an ink edge, and thicker icon lines, so "on" never relies on color alone. In Windows' high contrast modes (forced colors), it uses the system's highlight color, for hover too.
- **Every toolbar button** is a full `--target-min` square: 24px with a mouse and 44px on a touch screen. Each one is a whole target, so neighbors never take each other's clicks.
- **The height** grows with the text. CSS's `lh` unit is one line's height. The editable area is at least `rows` lines plus padding, and at most `maxRows` lines, then it scrolls. The padding is `(--control-md − 1lh) / 2` above and below, so one line is exactly as tall as an Input, and the two line up in a form. `rows` and `maxRows` reach the CSS as the custom properties `--rich-text-rows` and `--rich-text-max-rows`.
