# How Button works

There are two components here. `Button` does something: it sends, saves, or opens. `ButtonLink` goes somewhere: it's a link that looks like a button. They look the same because they share their props, their insides, and their CSS. Which variant, size, and shape to pick is on [Choosing a button](?path=/docs/components-button--choosing-a-button). This page is about how they work.

They're made of these files:

**Base UI** is an unstyled React library that handles behavior and accessibility, and leaves the look to us. For a button there's little to handle, because the browser's `<button>` already does most of it. Base UI's Button adds three things Button uses: it sets `type="button"`, it can keep a disabled button focusable, and it marks the disabled state with a `data-disabled` attribute for the CSS. ButtonLink doesn't use it: Base UI's own docs say a link should be styled as a link, not passed into its Button.

Every code block on this page is read from those files when the page loads, so it's always the code that runs. The demos use the real components.

### The props

The props both components share are in `shared.tsx`. `variant`, `size`, and `shape` are each a fixed set of strings (the types `ButtonVariant`, `ButtonSize`, and `ButtonShape` at the top of the file), so a typo such as `variant="primay"` doesn't compile:

The comment above each prop is its documentation: Storybook shows it in the props table on the Docs page, and your editor shows it when you hover the prop.

Button's own props start from those and add Base UI's:

<Code file="components/Button/Button.tsx" name="ButtonProps" />

`Omit<…>` takes some of Base UI's props away:

- **`className`.** Base UI also accepts a function that returns a class from the button's state. Button only takes a string, and adds its own class to it.
- **`render`.** Base UI's `render` prop swaps the `<button>` for another element. Without it, Button is always a `<button>`, and nobody can pass in an `<a>`, which Base UI's docs warn against. That's what ButtonLink is for.
- **`nativeButton`.** It only matters with `render`.
- **`keyof SharedProps`, `aria-label`, and `tone`.** These are defined by `SharedProps`, `IconOnly`, and `Toned`, so Base UI's versions (where it has one) are taken out to leave one definition of each.

Everything else Base UI's Button accepts, which is every attribute a `<button>` can have (`type`, `name`, `onClick`, and so on), passes straight through. `ref` is an ordinary prop in React 19, so there's no `forwardRef`.

### Danger only where it can work

`tone="danger"` marks an action that destroys or loses something. It's only allowed where it can be seen clearly and say what's lost, and the type enforces that:

<Code file="components/Button/Button.tsx" name="Toned" />

Like `IconOnly`, it's a union of two shapes. The first is the ordinary button, with `tone` left out or `"neutral"`. In the second, `tone` is `"danger"`, `variant` must be `"secondary"` or `"ghost"`, and `iconOnly` can't be `true`. So `<Button tone="danger">Delete</Button>` doesn't compile (the default variant is primary), and nor does a danger icon-only button, which would have no words to say what will be lost. Choosing a button explains when to use it.

### An icon-only button must have a name

An **accessible name** is what a screen reader says a control is called. A button with text is named by its text. An icon-only button has no text, so it needs an `aria-label`. The type makes sure it has one:

<Code file="components/Button/shared.tsx" name="IconOnly" />

This is a union of two shapes, and the props must match one of them. In the first, `iconOnly` is `false` or left out, and `aria-label` is optional. In the second, `iconOnly` is `true` and `aria-label` is a required `string`. So `<Button iconOnly><Heart /></Button>` doesn't compile: TypeScript can't match it to either shape. Each shape has its own comments, so the docs table describes `aria-label` in both cases.

The type can't catch everything. It doesn't require label text on a button that isn't icon-only, and `aria-label=""` is a string, as is a label that came back empty from a CMS. Each of these leaves a button with no name, so Button checks again while it renders:

<Code file="internal/warn.ts" name="hasContent" />

### The component

<Code file="components/Button/Button.tsx" name="Button" />

From top to bottom:

- **Defaults.** `variant = "primary"`, `size = "md"`, `shape = "rectangle"`, and `tone = "neutral"` are filled in when the props are left out, so every button renders all four attributes.
- **The name check.** For an icon-only button, Button passes `undefined` as the label, because its children are the icon, which is hidden. Only an `aria-label` can name it.
- **`{...rest}` first.** Everything else you pass goes on the element first, and Button's own attributes come after it. Later attributes win, so you can't override `data-variant` by accident.
- **`className`.** `cx()` joins Button's class and yours, so `className="mt-4"` renders `class="button mt-4"`:

<Code file="internal/cx.ts" name="cx" />

- **`|| undefined`.** `data-icon-only={iconOnly || undefined}` is `true` or `undefined`. React writes `true` as `"true"` and leaves `undefined` out. Without `|| undefined`, a normal button would render `data-icon-only="false"`, and the CSS selector `.button[data-icon-only]` would still match it, because it only checks that the attribute is there. `data-loading` and `aria-busy` work the same way.
- **Loading is a kind of disabled.** `disabled={disabled || loading}` disables a loading button, so it can't be pressed twice. `focusableWhenDisabled={loading}` tells Base UI to keep it focusable. So Base UI uses `aria-disabled` instead of `disabled`, and blocks it itself: it cancels clicks and pointer presses, and every key except Tab. A keyboard user who pressed it stays on it, and can Tab away as normal.

Both components put the same thing inside, from `shared.tsx`:

## 3. How it looks: `button.css`

All of Button's look is in one stylesheet, inside `@layer components`. CSS layers decide which styles win, whatever their specificity: the design system's order is `theme, base, components, utilities`, so a Tailwind utility in your markup, such as `w-full` to stretch a button across a form, beats the component's own CSS.

Every value comes from a **token**: a named design value, such as `--action` or `--control-md`, defined once in `tokens/tokens.json`. Button uses semantic tokens, which say what a value is for, rather than primitives, which say what it is (`--action` rather than `--gray-900`). Each theme points the semantic tokens at different primitives, so Button changes with the theme without any theme rules of its own. Its colors are neutral: black, white, and grays. The brand colors are for the layout around components, so the same buttons can serve other brands.

These work by **specificity**: when two rules set the same property, the one whose selector has more classes, attributes, and pseudo-classes wins. `.button[data-variant="secondary"]:hover` counts three. `.button[data-disabled]:not([data-loading]):hover` counts four (`:not()` counts what's inside it), so it wins and puts back the primary fill. ### The hit area

A button's **hit area** is everywhere a click or tap counts as pressing it. Every hit area in the design system is at least `--target-min` in both directions: 24px with a mouse, and 44px when the device has a touch screen. Fingers are less precise than a pointer. Most buttons are already bigger than that, but a small button is only 32px tall, so on touch it would be too small.

So `.button::after` adds an invisible box around the button. A pseudo-element is part of its element, so clicking it is clicking the button:

<Code file="components/Button/button.css" name=".button::after" />

`position: absolute` places it relative to the button, which is `position: relative`. Its insets are measured from the button's padding box, the area inside its border, and `100%` is that box's height (or width, for the inline insets). Take a small button on a touch screen:

1. Its padding box is 28px tall: 32px minus the 2px border at the top and at the bottom.
2. `(100% - var(--target-min)) / 2` is (28 − 44) / 2 = −8px. A negative inset moves the edge outwards, so the box reaches 8px above and 8px below: 28 + 16 = 44px tall.
3. `min(0px, …)` takes whichever is smaller. With a mouse, (28 − 24) / 2 is +4px, and a positive inset would pull the box inside the button. `min()` keeps it at 0, so a button that's already big enough gets nothing extra.

The same rule works for width, so a small icon-only button gets a 44px square on touch. Here are the same buttons with a mouse and on touch, with each `::after` drawn as a dashed line. The sizes are measured from the page as you see it:

</Unstyled>

On touch, a medium button is already 44px tall, so its `::after` only reaches over its own border, and the dashed line hugs its edge.

`--target-min` changes with the device on its own. The tokens switch it to 44px when any touch input is present, or inside `data-pointer="coarse"`, which is how the demo shows touch on any device. Compact density (`data-density="compact"`) makes medium and large buttons smaller, but never below `--target-min`. Button never checks the pointer itself: it only reads tokens, so every mode works without changes. Because the hit area reaches past the button, leave at least `--target-gap` (8px) between small buttons, so their hit areas don't overlap. [Mouse, touch, and screen size](?path=/docs/foundations-mouse-touch-and-screen-size--docs) has the reasons behind the sizes.

### Hot dog mode

Hot dog is the joke theme, in ketchup and mustard. Its buttons get a thick ink outline and a hard shadow, and instead of lifting on hover, they push into the shadow when pressed:

<Code file="components/Button/button.css" name='[data-theme="hotdog"] .button:not([data-variant="ghost"])' />

<Code file="components/Button/button.css" name='[data-theme="hotdog"] .button:hover' />

<Code file="components/Button/button.css" name='[data-theme="hotdog"] .button:not([data-variant="ghost"]):active:not([data-disabled])' />

In hot dog, `--shadow-sm` is a solid shadow 2px right and 2px down. Pressing moves the button 2px right and 2px down and takes the shadow away, so the button lands exactly where its shadow was. Ghost buttons have no outline or shadow, so they don't press. Neither do disabled or loading ones, which have `data-disabled`.

Try all three themes here. The switch turns on reduced motion for the demo only:

</Unstyled>

### Forced colors

Windows' Contrast themes replace every color on the page with a few system colors the person chose, and remove shadows and background images. This is called **forced colors**. Without care, a ghost button would become plain text, and the hot dog shadow would vanish.

<Code file="components/Button/button.css" name="@media (forced-colors: active)" />

- The transparent border becomes a real one, in `ButtonText`, the system's color for button text and edges. Every button, ghost ones and links too, shows its edge.
- A disabled button turns `GrayText`, the system's color for disabled things. Its opacity goes back to 1, because dimming the system's colors could make them hard to read.
- Focus is still visible, because it's an outline. The spinner is still visible, because it's drawn in `currentColor`.

To see it without Windows, open Chrome's DevTools, open the Rendering panel, and set "Emulate CSS media feature forced-colors" to "active".

### Motion

`.button` transitions its colors, border, shadow, and position over `--duration-fast` (120ms) with `--ease-out`, which starts fast and slows down. So the hover lift and the fill change ease in rather than jump.

When someone has asked their system for reduced motion, two tokens change, and Button needs no rules of its own:

- `--motion-distance` becomes 0, so the hover lift is 0 and the button stays still. The fill still changes.
- `--duration-loop` goes from 700ms to 1600ms, so the spinner turns more slowly. It doesn't stop, so it still shows that something is happening.

The hot dog press isn't built from `--motion-distance`, so it still moves under reduced motion. Setting `data-motion="reduced"` or `data-motion="full"` on any element overrides the system setting inside it, as the switch in the demo above does.

## 4. Keyboard and screen readers

<div className="button-parts">
<table>
  <thead>
    <tr><th>Key</th><th>Button</th><th>ButtonLink</th></tr>
  </thead>
  <tbody>
    <tr><td>Tab, Shift+Tab</td><td>Moves focus to it and away. A disabled button is skipped. A loading one isn't.</td><td>Moves focus to it and away.</td></tr>
    <tr><td>Enter</td><td>Presses it.</td><td>Follows the link.</td></tr>
    <tr><td>Space</td><td>Presses it.</td><td>Scrolls the page, as on any link. Links don't respond to Space.</td></tr>
  </tbody>
</table>
</div>

All of this comes from the browser, because Button is a real `<button>` and ButtonLink a real `<a>`. Base UI only steps in for a loading button, where it blocks Enter and Space but lets Tab through.

A screen reader announces:

- **The name.** The label text, or the `aria-label` of an icon-only button. Icons and the spinner are hidden, so they're never read out.
- **The role.** "Button" for Button and "link" for ButtonLink. This is why ButtonLink exists: someone who hears "link" knows it goes somewhere, and can open it in a new tab.
- **The state.** A disabled or loading button is announced as unavailable ("dimmed" in VoiceOver). Base UI's docs warn that some browser and screen reader pairs don't announce a change to the text of a button that has focus, such as "Send message" becoming "Sending message". If it matters that people hear the change, announce it somewhere else as well, such as in a status message.
