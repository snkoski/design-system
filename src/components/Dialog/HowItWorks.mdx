# How Dialog works

A dialog is a window over the page for a short task, such as "Edit profile", or a question that needs an answer, such as "Delete project?". This page walks through the real code underneath Dialog, AlertDialog, and DialogClose: what HTML they render, how each prop gets there, and how the CSS draws them. Every code block is read from the source files when the page loads, so it's always the code that ships, and every demo is the real component.

## What it's made of

All three are built on [Base UI](https://base-ui.com), an unstyled React library that handles behavior and accessibility. For a dialog that's most of the work: moving focus in and keeping it there, closing with Escape, hiding the rest of the page from screen readers, stopping the page from scrolling, and giving focus back when it closes. Our code chooses the parts, connects the props to them, and adds the look.

None of these layers has a `z-index`. They're last in `<body>`, so they're drawn over the page, as long as the app's own root has `isolation: isolate`: then anything the app stacks with `z-index`, such as a fixed header, stays inside the root, below the dialog. README and **Choosing a dialog** say so.

Two things change outside the dialog too. Everything else on the page gets `aria-hidden="true"`, so screen readers can't wander out of the window (and `data-base-ui-inert`, Base UI's own marker; it isn't the HTML `inert` attribute). Nothing outside can be clicked, because the clear layer covers it, or reached with Tab, because of the focus guards. And `<body>` gets `overflow: hidden` (with `scrollbar-gutter: stable` on `<html>`, so the page doesn't shift sideways when its scrollbar goes), so the page behind doesn't scroll.

### The close button comes last

The X is drawn in the top corner, but it's the last thing in the window's HTML. When a dialog opens, Base UI moves focus to the first thing in it that can take focus. With the X first, every dialog would open with focus on "Close". Last, focus starts on the first field, or on "Cancel" when there are no fields: the least destructive answer, as **Accessibility** asks.

### `aria-modal`

Base UI doesn't set `aria-modal="true"`; it hides the rest of the page itself instead. We add it anyway. It says the same thing in the way screen readers and checkers expect, and without it, axe (the checker every story runs) doesn't treat an alert dialog as modal, so it flags the hidden focus guards as focusable content hidden from screen readers.

## When the body scrolls

When the content is taller than the space, the body scrolls on its own while the title and buttons stay. A keyboard user can only scroll something that has focus. Inside a form, the fields take focus, and the browser scrolls each one into view. With only text inside, nothing can, so the body itself needs `tabindex="0"`. But if the body always had it, it would be the first thing in the window and take the first focus from the fields. So it gets one only while it scrolls with nothing inside to Tab to. Open this one and watch `tabindex` appear on the body.

## A form in a dialog

With `onSubmit`, the body and the buttons go inside one `<form>`, so Enter in a field submits it, and so does a `type="submit"` button among the actions. The form has `display: contents`, so it doesn't change the layout. Submitting doesn't close the dialog: this handler reads the form, then closes it.

### The components

Dialog sorts its props. The ones about opening and closing go to Base UI's root. `trigger` becomes the trigger, through Base UI's `render` prop: Base UI renders your Button, with its own attributes merged in. `Frame` draws everything inside the root. It leaves out an empty title (an empty heading would still be what names the window, over any `aria-label`), the body when there are no children, and the actions when there are none. With `onSubmit`, the body and actions go in a form.

## How it looks

### The dimmed page

The backdrop covers the screen in `backdrop`, a see-through near black: the only color token with transparency.

### Centering, with a gutter

The viewport covers the screen too, and centers the window in a single grid cell. Its padding is the gutter between the window and the screen's edges. The cell is set to the size of the screen, so the window's `max-height: 100%` means "the screen, less the gutter".

### The window

The window is as wide as its size allows, and no wider than the viewport. It's a column: header, body, and actions. The border is there even where the shadow seems to be enough, because Windows high contrast removes shadows.

The sizes are tokens: `dialog-sm` (400px), `dialog-md` (600px, the default), and `dialog-lg` (800px). On a screen narrower than that, `width: 100%` and the gutter take over.

### Opening and closing

Base UI marks the window and backdrop with `data-starting-style` as they appear and `data-ending-style` as they leave, so plain CSS transitions can animate both ways. The window fades in and rises by `--motion-distance`, over `--duration-slow`. It leaves faster, over `--duration-base` with `--ease-in`, as everything in the system does. Under reduced motion, `--motion-distance` is 0 and both durations shrink to 120ms, so it only fades, with no change to this CSS.
