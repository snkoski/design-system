# How File input works

A file input is a field for choosing files from the device to send with a form. It's the browser's own `<input type="file">`: the browser draws its "Choose file" button and the words beside it, opens the system's file picker, and sends the files with the form. Around it, it's a text field like [Input](?path=/docs/components-input--how-it-works): the same label, help text, error, edge, states, and themes. It adds one thing the browser's input can't do: once a file is chosen, a Remove button empties the field again. This page covers what's different, and links to the Input page for the rest. Every code block is read from the source files when the page loads, so it's always the code that ships, and every demo is the real component.

It uses Base UI's `Field.Root`, `Field.Label`, `Field.Description`, `Field.Error` (through `FieldError`), and `Input`, as Input does, and Base UI's `Button` for Remove. [Base UI](https://base-ui.com), the unstyled library underneath, links the label and help text to the input and handles the ARIA attributes. Base UI has no file component of its own.

The chosen files don't show in the HTML. They live in the input's `files` property, and the words beside the button ("No file chosen", "cv.pdf", "2 files") and the button itself are drawn by the browser, inside the input, where no HTML or CSS class reaches them. CSS reaches the button through one pseudo-element, `::file-selector-button`; nothing reaches the words but the input's own font and color.

Some things to notice:

- **Counting files.** The only state is how many files are chosen, read from the input, never assumed: once when it first renders (a browser can put files back after the Back button), on every change, and after a form reset. A reset empties the input without a change event, and fires before it empties it, so the count is read on the next turn.
- **Remove** sets the input's value to `""`, the one value a page may give a file input, then fires `input` and `change`, as a person's choice does, so `onChange`, `onFilesChange`, form libraries, and anything else listening hear it. Then focus goes back to the input.
- **A file dropped on Remove** goes to the field. Remove sits over the field's end, so a file dragged there lands on the button, not the input, and the browser would otherwise open the file in the tab and leave the form.

## Keyboard, screen readers, and forms

**Keyboard.** It's the browser's own file input: Tab moves to it, and Enter or Space opens the system's file picker, as a click anywhere on the field does. While a file is chosen, Remove is the next Tab stop; Enter or Space empties the field and moves focus back to it. A disabled field, and its Remove, are skipped by Tab.

**Screen readers** announce the label as its name, that it's a button (the words depend on the screen reader and browser), the browser's status ("No file chosen", the file's name, or how many), then the description and any error.

**Browsers** write their own words, in their own language: Chrome and Edge say "Choose File" and "No file chosen", Firefox "Browse…" and "No file selected.", and Safari "Choose File" and "no file selected". Safari puts its words a little closer to the button than the CSS asks for.
