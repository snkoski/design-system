# How Switch works

A switch turns one setting on or off, such as "Email me about new projects". This page walks through the real code underneath it: what HTML it renders, how each prop gets there, and how the CSS draws it. Every code block is read from the source files when the page loads, so it's always the code that ships, and every demo is the real component.

## What it's made of

Switch is a thin layer over [Base UI](https://base-ui.com), an unstyled React library that handles behavior and accessibility: keyboard use, focus, ARIA attributes, and taking part in forms. Our code chooses the parts, connects the props to them, and adds the look.

A choice control (a checkbox, radio, or switch) puts its description under the label, next to what it describes. A text field puts it between the label and the field instead, so it's read before typing: see [How Input works](?path=/docs/components-input--how-it-works).

### Invalid, with an error

This switch is `required`, `invalid`, and has a description and an `error`.

<Unstyled>
  <Inspect hint="Turn it on: the error stays, because invalid is a prop. Only the page using the switch decides when it's valid.">
    <Switch required invalid description="Anyone with the link can see it." error="Turn this on to publish your portfolio.">
      Share my portfolio publicly (required)
    </Switch>
  </Inspect>
</Unstyled>

- `aria-invalid="true"` is on the switch and on the hidden input. Our code never writes it: we pass `invalid` to `Field.Root`, and Base UI passes it on.
- `aria-describedby` now holds two ids, the description's and the error's, so both are read.
- `required` sets `aria-required="true"` on the switch, for screen readers, and the native `required` on the hidden checkbox, for the form's validation.
- The error is a `<div class="field-error switch__error">` with an icon and words, so the problem is never only a red edge. It's drawn by the shared `FieldError`, which [How Checkbox works](?path=/docs/components-checkbox--how-it-works) explains in full, along with the development warnings.

### Disabled and read-only

<Unstyled>
  <Inspect hint="Try clicking each one, and pressing Tab: only the read-only switch takes focus, and none of them change.">
    <div className="grid gap-1">
      <Switch disabled>Off and disabled</Switch>
      <Switch disabled defaultChecked>On and disabled</Switch>
      <Switch readOnly defaultChecked>Two-step sign-in</Switch>
    </div>
  </Inspect>
</Unstyled>

- **Disabled.** A `<span>` has no `disabled` attribute, so Base UI uses `aria-disabled="true"` to tell screen readers, and `tabindex="-1"` to take it out of the Tab order. The hidden checkbox gets a real `disabled`, so the form leaves it out. Every part, from the wrapper to the thumb, gets `data-disabled`.
- **Read-only.** Base UI sets `aria-readonly="true"` and `data-readonly`, keeps `tabindex="0"`, and ignores clicks and keys itself. The switch stays in the Tab order, so someone using a screen reader can still find it and hear whether it's on. The label gets a "Read only" note with a lock, hidden from screen readers, which already announce it. The shared `ReadOnlyNote` draws it, and [How Checkbox works](?path=/docs/components-checkbox--how-it-works) explains it.

### In a form

The first switch here has `uncheckedValue="no"`, and the second doesn't.

<Unstyled>
  <Inspect hint="Turn Newsletter on and off, and watch a second hidden input come and go. Then select Save settings.">
    <SettingsForm />
  </Inspect>
</Unstyled>

While Newsletter is off, Base UI adds `<input type="hidden" value="no">` with the same `name`. A checkbox that's off submits nothing, so this extra input is how an off switch can still send a value. When it's on, the extra input goes, and the checkbox sends `value`. Project alerts has no `uncheckedValue`, so turning it off makes it disappear from what the form sends, as a native checkbox would.

The checkbox's `checked` attribute only shows how it started. Turn Newsletter on and the attribute doesn't appear: React sets the live state as the input's `checked` property, which isn't part of the HTML, and the property is what the form reads.

## From props to HTML

### The props

A switch must have a name a screen reader can announce. The props type makes that a compile error rather than something to remember:

<Code file="components/Switch/Switch.tsx" name="Labelled" />

It's a union, which TypeScript reads as "one of these": either `children` (the visible label), or an `aria-label`. Leave out both and the code doesn't compile. The label's type is `Exclude<ReactNode, undefined | null | boolean>`, all of React's renderable content except the values that render nothing. Plain `ReactNode` would accept `undefined`, and a nameless switch would compile.

An empty string still gets through, such as a label from a content system that came back blank. That's what `warnIfUnnamed()` is for. It prints a warning in development when the label renders nothing and there's no `aria-label`. [How Checkbox works](?path=/docs/components-checkbox--how-it-works) explains when the system warns and when it doesn't.

<Code file="components/Switch/Switch.tsx" name="OwnProps" />

Most of these are Base UI's own props, declared again here with our JSDoc. Storybook builds the docs table from the component's own types and doesn't read types inherited from `node_modules`, so a prop that isn't declared here wouldn't appear in it.

<Code file="components/Switch/Switch.tsx" name="SwitchProps" />

The full props type is the label union, our props, and whatever else Base UI's `Switch.Root` takes, less a few things we want to control ourselves:

- `className` goes on the outer wrapper, not the track, so a layout class such as a margin lands on the whole field.
- `render` and `nativeButton` would let someone swap the `<span>` for another element. Base UI renders a `<span>` by default so the switch can sit inside its `<label>`, so they're kept out.
- `children` and `aria-label` are left out because `Labelled` declares them.

### The component

<Code file="components/Switch/Switch.tsx" name="Switch" />

Reading it top to bottom:

1. **Pulling props apart.** `children`, `description`, `error`, `invalid`, `className`, `disabled`, and `name` are taken out, because they go somewhere specific. Everything else (`checked`, `defaultChecked`, `onCheckedChange`, `readOnly`, `required`, `value`, `uncheckedValue`, `id`, `form`, `ref`, `inputRef`, and `aria-label`) stays in `rest` and goes straight to `Switch.Root`, which turns them into the attributes you saw above.
2. **The warning.** `warnIfUnnamed()` runs during render, so it also works when a page is rendered on a server.
3. **The control.** `Switch.Root` gets the class `switch__track`, and `Switch.Thumb` sits inside it. `disabled` and `name` go to both `Field.Root` and `Switch.Root`, so the field and the control always agree.
4. **The label.** With `children`, the control and the label text go inside `Field.Label`, which makes the whole row clickable. With only an `aria-label`, the control is rendered on its own, with no `<label>` element at all.
5. **The description and error** render only when they're given. `invalid` goes to `Field.Root`, which sets `aria-invalid` and links the error. `FieldError` gets `match={invalid}`, so the message only shows while the switch is invalid.

## How it looks

The switch's look is in three files, all inside `@layer components`. What it shares with Checkbox and Radio is in `internal/choice.css`, and its description's look in `internal/field.css`, so a fix there is a fix to all of them; [How Checkbox works](?path=/docs/components-checkbox--how-it-works) explains those rules in full. Each part carries a shared class next to its own, such as `class="choice__control switch__track"` on the track. `switch.css` has only what's the switch's own, and it's imported after the shared files, so it wins where they set the same thing. Layers set which CSS wins regardless of how specific a selector is, and the order is `theme, base, components, utilities`. So a Tailwind utility in the markup (in `utilities`) can override a component for a one-off.

The switch only uses **semantic tokens**, named for their job rather than their color: `surface`, `surface-hover`, `border-strong`, `action`, `action-hover`, `on-action`, `ink`, `ink-muted`, `focus`, and `danger`. Each theme gives them its own values. All but `danger` point at the gray scale, so components stay neutral and the brand colors live in the layout around them. `danger` is a status color, used where it carries meaning.

### Sizes from tokens

The track is `--choice` tall (24px) and 1.75 times as wide (42px). The width is stored in `--switch-track-width` because the thumb's travel and the description's indent are worked out from it.

<Code file="internal/choice.css" name=".choice__row" />

<Code file="internal/choice.css" name=".choice__label" />

The row is the label, and it's `--choice-row` tall: 32px with a mouse, and 44px when the device has a touch screen. The padding above and below is half of what's left after the 24px track, so the track sits on the label's first line, which is also 24px tall. If the label wraps onto more lines, the track stays beside the first one.

<Code file="internal/choice.css" name=".choice__control" />

<Code file="components/Switch/switch.css" name=".switch__track" />

The track has a `border-thick` edge in `border-strong`, which meets 3:1 contrast in every theme on its own, whatever the fill is. So the switch shows clearly when it's off, and the edge never relies on the fill. `box-sizing: border-box` keeps the edge inside the 24 × 42px box.

<Code file="internal/choice.css" name=".choice__control::after" />

Every interactive target is at least `--target-min` in both directions: 24px with a mouse, 44px on touch. When there's a label, the row already meets it. Without one, this invisible pseudo-element stretches the track's hit area. An absolutely positioned child is placed from inside its parent's border, so the inset is half of `--choice - --target-min`, less the 2px edge. With a mouse that's -2px, exactly the track's own 24px. On touch it's -12px, giving 44px.

<Code file="internal/choice.css" name=".choice:not(:has(> .choice__row))" />

On touch, that 44px area is taller than the 24px track, and would spill into a control above or below. So a switch without a label pads its own wrapper to `--choice-row`, which keeps neighbors' hit areas apart.

Text never changes size with the pointer. And compact density (`data-density="compact"`) changes only `--control-md` and `--control-lg`, which a switch doesn't use: `--choice` and `--choice-row` stay the same.

### On and off

<Code file="components/Switch/switch.css" name=".switch__thumb" />

<Code file="internal/choice.css" name='.choice__control[aria-checked="true"]' />

<Code file="components/Switch/switch.css" name='.switch__track[aria-checked="true"] .switch__thumb' />

On fills the track with `action` and turns the thumb `on-action`. The state is styled from `aria-checked`, the attribute screen readers read, so the look and what's announced can't disagree. Base UI's `data-checked` says the same thing, but the system styles from the ARIA attribute whenever one exists.

The fill isn't the only sign. The thumb also moves to the other end, so the state never relies on color alone. The distance is the track's width less `--choice`: 42 − 24 = 18px. That's the inside of the track (42px, less two 2px edges and two 2px paddings, is 34px) less the 16px thumb.

### Motion that shows state

The slide uses `--duration-fast` (120ms) and `--ease-bounce`, a curve that goes past the end and springs back. That bounce is one of the few places the system allows it: chips, toggles, and success states.

Most movement in the system is decoration, and slides use `--motion-distance`, which becomes 0 when someone has asked their device for reduced motion. A switch's slide isn't decoration: it's how the switch shows on and off. So the distance is fixed, and it still moves under reduced motion. What changes there is the curve: `--ease-bounce` becomes a plain ease-out, so it slides into place without overshooting. `--duration-fast` stays the same, because it's already short.

You can test this without changing your device's setting: `data-motion="full"` or `data-motion="reduced"` on any element sets motion for everything inside it. The demo below puts the same switch in each, and reads the thumb's position from the page every frame.

### Hover, focus, and invalid

<Code file="internal/choice.css" name='.choice__row:hover .choice__control:not([data-disabled], [aria-readonly="true"], [data-readonly])' />

<Code file="internal/choice.css" name='.choice__row:hover .choice__control[aria-checked="true"]:not([data-disabled], [aria-readonly="true"], [data-readonly])' />

Hovering anywhere on the row changes the track's fill: `surface-hover` when off, `action-hover` when on. The `:not()` leaves out disabled and read-only switches, which can't change, so they shouldn't look as if they will.

<Code file="internal/choice.css" name=".choice__control:focus-visible" />

Focus is an **outline**, never only a shadow, so it survives Windows high contrast. `:focus-visible` shows it when the browser judges that focus should be visible, such as after the Tab key, and not after a mouse click.

<Code file="internal/choice.css" name='.choice__control[aria-invalid="true"]' />

Invalid changes the edge to `danger`. Hover only changes the fill, so a hovered invalid switch keeps its red edge. (A text field's hover changes its edge, so it has to leave invalid out: see [How Input works](?path=/docs/components-input--how-it-works).)

### Disabled and read-only

<Code file="internal/choice.css" name='.choice__control[aria-readonly="true"]' />

<Code file="internal/choice.css" name=".choice__row[data-disabled]" />

The cursor says what will happen: `default` for read-only, because nothing will, and `not-allowed` for disabled.

- **Disabled** also sets `opacity: 0.5` on the track and on the label text.
- **Read-only** doesn't dim: the switch and its label stay at full strength, because read-only content must stay readable. The cue is the "Read only" note beside the label.

Disabled is styled from Base UI's `data-disabled` rather than `aria-disabled`. Base UI puts `data-disabled` on every part (the wrapper, the label, the track, and the thumb), so one attribute reaches the label too. ARIA's read-only state, `aria-readonly`, is on the track, so read-only is styled from that.

The description is indented by the track's width plus the gap, so it lines up with the label text rather than the track. The error isn't: it sits above the whole row, at its start.

### Hot dog mode

<Code file="internal/choice.css" name='[data-theme="hotdog"] .choice__control' />

<Code file="internal/choice.css" name='[data-theme="hotdog"] .choice__row:active .choice__control:not([data-disabled], [aria-readonly="true"], [data-readonly])' />

Hot dog mode, the system's ketchup-and-mustard joke theme, gives controls a hard offset shadow. In hot dog, `--shadow-sm` is a 2px solid shadow down and to the right. Pressing a switch (`:active`) moves it 2px into its shadow and drops the shadow, like a button. Text fields keep their shadow: you type in them rather than press them.

### Windows high contrast

<Code file="internal/choice.css" name="@media (forced-colors: active)" />

<Code file="components/Switch/switch.css" name="@media (forced-colors: active)" />

In forced colors mode (Windows Contrast themes), the browser replaces the page's colors with a few system colors, and drops shadows and most fills. The track's border is what keeps it visible, which is why every control has one. These rules choose the system colors on purpose:

- The track is `Canvas` with a `ButtonText` edge, and the thumb is `ButtonText`.
- On fills the track with `Highlight` and turns the thumb `HighlightText`, so on and off still differ.
- The hover selectors are repeated for the on state. A hover rule is more specific than `.choice__control[aria-checked="true"]`, so without them, hovering an "on" switch would win, turn the track back to `Canvas`, and hide the thumb.
- Opacity is reset to 1, and disabled uses `GrayText` instead.

## Keyboard, screen readers, and forms

**Keyboard.** Tab moves focus to the switch: the `<span>` with `tabindex="0"`, never the hidden input. Space or Enter turns it on or off. A disabled switch is skipped. A read-only switch takes focus, but Space and Enter do nothing.

**Screen readers** announce it as a switch, with its label as its name, whether it's on or off, and then its description and error. If it's `required` or `invalid`, they say so too.

**Pointer.** The whole label row is the click target. Base UI makes sure a click on the switch inside its label changes it once, not twice: a test checks it.

**Forms.** What `FormData` gets, from the hidden inputs:

<table>
  <thead>
    <tr><th>The switch is</th><th>What the form sends</th></tr>

    <tr><td>Off</td><td>Nothing</td></tr>

`form` names a `<form>` by its id, for a switch that sits outside it. `id` goes on the hidden input, not on the visible switch. A `<label htmlFor>` pointing at it would turn the switch on, but wouldn't name it for screen readers, so name it with `children` or `aria-label`.
