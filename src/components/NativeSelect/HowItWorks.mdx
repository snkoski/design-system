# How Native select works

A native select is a field for choosing one option from a list, drawn by the browser's own `<select>`. The browser opens the list (on a phone, its own picker), handles the keyboard, and submits the value with the form. Around it, it's a text field like [Input](?path=/docs/components-input--how-it-works) and [Text area](?path=/docs/components-text-area--how-it-works): the same label, help text, error, edge, states, and themes. This page covers what's different, and links to the Input page for the rest. Every code block is read from the source files when the page loads, so it's always the code that ships, and every demo is the real component.

It uses the same Base UI parts as TextArea: `Field.Root`, `Field.Label`, `Field.Description`, `Field.Error` (through `FieldError`), and `Field.Control`. [Base UI](https://base-ui.com), the unstyled library underneath, handles linking labels and help text, ARIA attributes, and forms. Base UI's own `Select` is a different thing: a list it draws itself, for options that need more than text. This one is the browser's.

The chosen option doesn't show in the HTML: like a text field's text, it lives in the select's `value` property. `selected` isn't written onto an `<option>` either, because React sets it as a property.

## From props to HTML

### The options

<Code file="components/NativeSelect/NativeSelect.tsx" name="NativeSelectGroup" />

The options are data, not children. An `<option>` can only show plain text, so a `label` string is all it needs, and the component can see every option: that's how it can warn about a value that matches none of them. RadioGroup and CheckboxGroup take their options as children, because each one is a whole component with its own label, which can hold anything.

The same union as Input's and TextArea's: a `label`, or an `aria-label`, or the code doesn't compile.

<Code file="components/NativeSelect/NativeSelect.tsx" name="NativeSelectProps" />

The type is built from React's `SelectHTMLAttributes`, so it takes exactly a select's attributes, and its events are typed for a `<select>`. Five are left out:

- `className` goes on the wrapper, as on every form control.
- `children`, because the options come from `options`.
- `size`, because the select's own `size` is a number that turns it into an always-open list box. Our `size` is `md` or `lg`.
- `multiple`, which would make the value a list. To choose several, use a CheckboxGroup.
- `readOnly`, because browsers ignore it on a select: the value still changes and is submitted, and screen readers aren't told. A read-only select is an open question in `docs/revisit.md`.

### The component

<Code file="components/NativeSelect/NativeSelect.tsx" name="NativeSelect" />

Reading it top to bottom:

1. **Pulling props apart.** The props declared in `OwnProps` are taken out, with `size = "md"`. Then `readOnly`, `multiple`, and `children` are taken out of what's left and thrown away. TypeScript already refuses them, but JavaScript can still pass them, and each would break something: a do-nothing `readonly`, a value that's suddenly a list, or options replaced by whatever was passed.
2. **Warnings.** `warnIfUnnamed` catches an empty label, as in every form control, and `warnIfNoMatch` (below) catches a value that matches no option.
3. **The options** become `<option>` and `<optgroup>` elements, keyed by their value (a group by its label), so when the list changes, React moves each element rather than rewriting it in place. Rewritten in place, an uncontrolled select's choice would jump to whichever option now sat there, and the form would send a value nobody picked. A repeated value gets a count added to its key.
4. **The wrapper, label, description, and error**, as in TextArea.
5. **The field.** `Field.Control` renders our `<select>`, exactly as TextArea's renders a `<textarea>`: every prop goes through `Field.Control`, so Base UI can merge a page's `aria-describedby` with the field's own description and error, and only the `<option>`s go on the `render` element. [How Text area works](?path=/docs/components-text-area--how-it-works) explains why that split matters.

### A value that matches no option

<Code file="components/NativeSelect/NativeSelect.tsx" name="warnIfNoMatch" />

If `value` is `"hired"` and no option has that value, React doesn't show an empty select: it quietly chooses the first option it can. The page thinks the value is "hired", the screen shows "Saved", and the form sends "saved". Nothing on the page looks broken, so this prints a development warning, once per value, saying what's wrong and how to fix it. It stays quiet before any options have arrived, because options are often still loading, and it counts a disabled option as a match, because React still chooses that one.

Loading has a catch of its own. React applies `defaultValue` once, when the select first appears. If the options arrive later, the browser chooses the first one, whatever `defaultValue` said. So a second warning fires when the options arrive after a `defaultValue` was set: pass `value` while they load, or render the select once they have. A controlled `value` doesn't have this problem, because React applies it on every render.

## How it looks

The look is in two files, inside `@layer components`. The label, description, edge, hover, focus, invalid, disabled, hot dog, and forced colors rules are shared with Input and TextArea in `internal/text-field.css` and `internal/field.css`: the select carries the shared class next to its own (`class="text-field__control native-select__control"`). [How Input works](?path=/docs/components-input--how-it-works) walks through each shared rule. `native-select.css` has only what's different.

### The field

<Code file="components/NativeSelect/native-select.css" name=".native-select__control" />

The height is `--control-md`, the same as an Input, so a select and a text field line up side by side. `appearance: none` removes the browser's own arrow and look, and the end padding leaves room for ours: the inset, the arrow, and a gap. A long option is cut off at that padding, so its words never run under the arrow.

<Code file="components/NativeSelect/native-select.css" name='.native-select[data-size="lg"] .native-select__control' />

Large works the same way with `--control-lg` and the larger inset. Because both read the size tokens, they follow touch screens (44px and 52px) and compact density (32px and 40px) with no rules of their own.

### The arrow

<Code file="components/NativeSelect/native-select.css" name=".native-select__icon" />

The arrow is Lucide's chevron, drawn inline in the component, as the error's and read-only note's icons are, so the package doesn't depend on an icon library. It sits over the select's end, the same distance in as an Input's end icon, and `pointer-events: none` lets a click on it through to the select. `inset-inline-end` is a logical property: on a right-to-left page it's the left end. The [Right to left](?path=/story/components-native-select--right-to-left) and [Long options](?path=/story/components-native-select--long-options) stories check both, with a real click test on the arrow.

<Code file="components/NativeSelect/native-select.css" name=".native-select[data-disabled] .native-select__icon" />

A disabled select dims to 50% from the shared rules, and the arrow, which sits outside the `<select>`, dims with it from the wrapper's `data-disabled`.

### The placeholder and the options

<Code file="components/NativeSelect/native-select.css" name=".native-select__control:has(.native-select__placeholder:checked)" />

While the placeholder is chosen, its words are muted, like a text field's placeholder. `:checked` matches the chosen `<option>`, and `:has()` lets the select ask whether its chosen option is the placeholder. Only the placeholder has that class, so an option of the page's own whose value is empty (an "Any" filter) stays at full strength.

<Code file="components/NativeSelect/native-select.css" name=".native-select__control option" />

The open list is the browser's. On macOS and phones, the system draws it and ignores these colors. On Windows and Linux, Chromium draws it with the select's own colors, so without this rule every option would turn muted while the placeholder is chosen. Each theme sets `color-scheme`, so the browser's list is dark in dark mode; in hot dog mode it's the light list, not ketchup and mustard. Styling the open list itself is an open question in `docs/revisit.md`.

### Windows high contrast

<Code file="components/NativeSelect/native-select.css" name="@media (forced-colors: active)" />

The shared rules give the field the system's field colors. The arrow takes the field's text color, or the system's disabled color, at full strength.

## Keyboard, screen readers, and forms

**Keyboard.** It's the browser's own `<select>`, so it works the way selects do everywhere: Tab moves to it; Space, Enter, or Alt+Down open the list, depending on the system; the arrow keys move through the options (on Windows and Linux they change the value without opening the list); and typing a letter jumps to the next option starting with it. A disabled select is skipped by Tab.

**Screen readers** announce the label as its name, that it's a pop-up button or combo box (the words depend on the screen reader), the chosen option, then the description and any error. If it's `required` or `invalid`, they say so too.
