# How Meter works

A meter shows how much of something there is, out of a known amount: "Topics done, 12 of 20". This page walks through the real code underneath it: the HTML it renders, how its props become attributes, and how the CSS draws the bar. Every code block is read from the source files when the page loads, so it's always the code that ships, and the demo is the real component.

## What it's made of

Meter is built on [Base UI](https://base-ui.com)'s Meter, which gives it the `meter` role and the value attributes screen readers read. Its look is shared with Progress: both carry the classes in `bar.css`, next to their own.

## The CSS, rule by rule

### The label row

The outer element is a grid: the meter, then the description. Inside the meter, the label and value share a row, the label taking the room and the value only what it needs. A long label wraps; the value never does, so the amount stays in one piece.

<Code file="internal/bar.css" name=".bar__value" />

### The track and its sizes

A rounded `track`-gray bar, 8px thick at `md` and 4px at `sm`. The size is the fill's height: the track uses `content-box`, so an edge (hot dog's, or forced colors') goes around the outside and never covers the fill. The track is faint against the page on purpose, like Skeleton's shapes: the words carry the exact amount.

<Code file="internal/bar.css" name=".bar__track" />

<Code file="internal/bar.css" name='.bar[data-size="sm"] .bar__track' />

### The fill

The fill is as wide as the whole track and slides in from the start: `--bar-value` says how far. It moves with `transform`, never by changing its width, so a change glides smoothly over `--duration-base` without the browser redrawing the layout, and the track clips it with its own rounded edge, so the fill's leading end stays round. On a right-to-left page it slides in from the right. Base UI sets a `width` on the fill for its own way of drawing it; Meter replaces it with `100%`.

<Code file="internal/bar.css" name=".bar__fill:dir(rtl)" />

### Tones

A tone colors the fill with a status color. Every fill is checked by `pnpm check` for 3:1 against the track in all three themes, the contrast a meaningful graphic needs. The words always say the status too.

<Code file="components/Meter/meter.css" name='.meter[data-tone="success"] .meter__fill' />

### Hot dog mode

A thick ink edge around the track, outside the fill, like hot dog's other components. No shadow: nothing here can be pressed.

<Code file="internal/bar.css" name='[data-theme="hotdog"] .bar__track' />

### Forced colors

Windows' forced colors mode removes background colors, which would leave no track and no fill. The track gets an edge in the text color, and the fill stays a solid block of it. Meter's tone rules are more specific than the shared rule, so meter.css repeats it for them.

<Code file="internal/bar.css" name="@media (forced-colors: active)" />

<Code file="components/Meter/meter.css" name="@media (forced-colors: active)" />

### No touch, density, or focus rules

Nothing about a meter can be pressed or focused, so it has no hit area, no focus ring, and nothing that changes with a touch screen or compact density.

## How it's tested

The unit tests check the role, name, and description, the value attributes and words, the default percent, clamping, where the fill sits, the tones and sizes, that the server's HTML already has the name and value, that it hydrates without a mismatch, refs, the empty-label warning, and the props type. The stories check what needs real CSS: that each fill covers its value's share of the track (also from the right, in a right-to-left page), each size's height with a mouse and on touch, each tone's color in all three themes, hot dog's edge, and that a long label wraps while the value stays on one line.
