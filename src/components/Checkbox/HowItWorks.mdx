# How Checkbox works

A checkbox is a box someone ticks or unticks, with its label beside it. This page walks through the code that makes one: the props you pass, the HTML they become, the CSS that draws it, and how it behaves with a keyboard, a screen reader, and a form.

Checkbox is also the pattern the other choice controls follow (Switch, Radio group, and Segmented control). So three pieces every form control shares are explained in full here: `FieldError`, the error message every control shows, `ReadOnlyNote`, the "Read only" note beside a read-only control's label, and the dev warnings.

Every code block on this page is read from the real files when the page loads, so it's always the code that runs. Every demo is the real component.

## 1. What it's made of

Checkbox doesn't write its own keyboard handling, focus management, or ARIA. It's built on [Base UI](https://base-ui.com), a library of React components that have behavior but no styles. ARIA is a set of HTML attributes, such as `role` and `aria-checked`, that tell assistive technology like screen readers what an element is and what state it's in. Base UI does the behavior. This design system adds the props, the look, and the rules on top.

**Why a span, and not a real checkbox input?** Base UI renders a `<span>` so a `<label>` can wrap it, and so CSS can draw it any way it likes. Base UI gives the span everything a native checkbox has for people: the role, the state, focus, and Space. A native `<input>` stays beside it for forms, hidden from everyone.

**How one click ticks once.** Clicking the box itself would normally make the label click its input too. Base UI cancels that, and clicks the hidden input itself. Clicking the label text is ordinary HTML: the browser clicks the input the label's `for` points at. Either way the input changes once, and Base UI listens for that change and updates `aria-checked`. A unit test checks that one click ticks once.

### Invalid, with an error

This is a small form that checks the box when it's sent, the way `docs/brand/forms.md` asks: validate on submit, then show the problem in words next to the field.

From the start, `required` gives the box `aria-required="true"` and `data-required`, and the hidden input the native `required`. When the form is sent with the box unticked, the demo sets `invalid` and these appear:

- `data-invalid` on the wrapper, the label, and the box, from `Field.Root`.
- `aria-invalid="true"` on the box and on the hidden input, so a screen reader announces it as invalid.
- The error, a `<div class="field-error checkbox__error">` with an id, an icon, and the words.
- That id, added to the box's `aria-describedby`. Base UI only adds it while the error shows, and takes it off when the error goes.

The error's `data-starting-style`, struck through a moment after it appears, is Base UI marking its first frame, so CSS could animate it in. `field-error.css` doesn't animate it.

The form has `noValidate`. Without it, the browser would check the native `required` itself, stop the form from being sent, and show its own message for the hidden input. `noValidate` turns that off, so the page checks and shows its own error.

### Disabled and read-only

<Unstyled>

- **Disabled** goes to both `Field.Root` and `Checkbox.Root`. Base UI adds `data-disabled` to the wrapper, the label, the box, and the mark. The box gets `aria-disabled="true"`, and `tabindex="-1"` takes it out of the Tab order. The hidden input gets the native `disabled`, which also means a form doesn't send it.
- **Read-only** gives the box `aria-readonly="true"` and `data-readonly`. It keeps `tabindex="0"`, so people can still Tab to it and hear its state. Base UI ignores clicks and Space. The hidden input isn't disabled, so a form still sends it. The label gets a "Read only" note with a lock, `aria-hidden`, so you can see it can't be changed before you try (see `ReadOnlyNote` in section 3).

## 3. From props to HTML

### The props type

A checkbox must have an accessible name: the words a screen reader says for it. The props type makes that a compile error to forget.

<Code file="components/Checkbox/Checkbox.tsx" name="Labelled" />

It's a union of two shapes. Either there's label content in `children`, and `aria-label` is optional, or there isn't, and `aria-label` is required. Leave out both and TypeScript refuses to compile.

The label's type is `Exclude<ReactNode, undefined | null | boolean>`. React's `ReactNode` includes `undefined`, `null`, `true`, and `false`, which all render nothing. Typed as plain `ReactNode`, `<Checkbox>{undefined}</Checkbox>` would compile and render a checkbox with no name. `Exclude` takes those four out. Each branch repeats its JSDoc comments, so Storybook's docs table describes both props whichever branch it reads.

<Code file="components/Checkbox/Checkbox.tsx" name="CheckboxProps" />

`OwnProps` lists the props this component declares and documents itself, because Storybook's docs table only reads props declared in this repo, not ones inherited from `node_modules`. Everything else comes from Base UI's `Checkbox.Root.Props`, minus a few:

- `className`, which goes on the wrapper here, not the box.
- `render` and `nativeButton`, which would swap the span for another element. The label, the CSS, and the hit area all depend on it being this span.
- `children` and `aria-label`, which `Labelled` types instead.

### The component

<Code file="components/Checkbox/Checkbox.tsx" name="Checkbox" />

It runs top to bottom on every render:

1. **Is it in a group?** `useContext(CheckboxGroupContext)` reads the group's context. Outside a group it's `null`.
2. **Set aside what a group owns.** `checked`, `defaultChecked`, `uncheckedValue`, and `required` are pulled out of `rest` into `groupable`, which is `rest` without them. On its own, the checkbox passes all of `rest` to Base UI. In a group, it passes only `groupable`, because the group's value decides what's ticked.
3. **Warn about mistakes** that TypeScript can't catch (see "Dev warnings" below).
4. **Build the box.** `BaseCheckbox.Root` gets the props spread first, then the ones this code decides. Later props win, so nothing in `rest` can override them. `name` is left off in a group, because the group's field names every option. `readOnly` is on if the checkbox or its group says so.
5. **Draw the mark.** `Checkbox.Indicator` takes a `render` function, which gets Base UI's `state`. For a "select all" box in a group, the group decides when it's mixed, so the mark reads `state.indeterminate` rather than the prop.
6. **Wrap it in its label.** With `children`, the box and the text go inside `Field.Label`. Without, the box stands alone. The description comes after.
7. **Make it a field.** On its own, it's a `Field.Root`, which takes `name`, `disabled`, and `invalid`, and holds the error. In a group, it's a `Field.Item`.

<Code file="components/Checkbox/Checkbox.tsx" name="Mark" />

The mark is drawn on a 16 by 16 grid. Its stroke is `currentColor`, the text color of the element it's in, so the CSS colors it by setting the box's `color`.

### Inside a group: the context and `Field.Item`

A [CheckboxGroup](?path=/docs/components-checkbox-group--how-it-works) makes several checkboxes one form field. The group has to tell each checkbox inside it that it's in a group, and React context is how: a value a parent provides that any component inside it can read, however deep, without passing props through every level.

<Code file="components/CheckboxGroup/context.ts" name="CheckboxGroupContextValue" />

<Code file="components/CheckboxGroup/context.ts" name="CheckboxGroupContext" />

Its default is `null`, so a checkbox outside a group reads `null`. Inside a group it reads `readOnly`, which it adds to its own, and `hasAllValues`, which it only uses to warn.

In a group, the group's `Field.Root` is the field: it owns the name, the invalid state, and the error. Base UI links each control to the nearest field around it. If each checkbox also rendered a `Field.Root` of its own, that would be the nearest one, and the checkbox would get its name and validity from there instead of from the group. So in a group it renders `Field.Item`, which is made for this: it gives an option its own label and description, and leaves the field to the group. Props the group owns, such as `name`, `invalid`, and `error`, are ignored there, and a dev warning says so.

### FieldError: the error every form control shows

Every form control in the system (Checkbox, CheckboxGroup, Switch, Radio group, Segmented control, Input, and TextArea) shows its error with this one component, so every error looks and reads the same.

<Code file="internal/FieldError.tsx" name="FieldError" />

<Code file="internal/FieldError.tsx" name="ErrorIcon" />

- **It's Base UI's `Field.Error`**, so Base UI gives it an id and adds that id to the control's `aria-describedby`, but only while it shows. A screen reader reads the error after the control's name and state.
- **`match` decides when it shows.** Each control passes its `invalid` prop. When `match` is `true`, Base UI always shows the message. Otherwise, Base UI would only show it if its own validation had failed, and these components don't use Base UI's validation. So in practice, `invalid` alone decides. A unit test checks the error is hidden when the checkbox is valid.
- **An icon and words.** The error is never only a red border. The icon is a warning triangle, Lucide's triangle-alert, drawn here because Lucide is only a development dependency. It's `aria-hidden`, because the words carry the meaning.
- **A hidden "Error:".** A control reads its description and its error one after the other, so without it a screen reader user can't tell where the hint ends and the problem starts. Sighted people already have the red, the icon, and the position, so the word is hidden from view but not from screen readers. The space after it is its own text node, between the two `<span>`s: a space inside the prefix would be trimmed when the parts are joined, and read as "Error:Enter".
- **`className`** is the control's own class for this part, such as `checkbox__error`, added next to `field-error`. The shared CSS draws it, and the control's CSS only places it.

Each control renders it only when there's an `error` to show, with `{error && …}`, so `invalid` with no message marks the box but adds no empty line.

<Code file="internal/field-error.css" name=".field-error" />

<Code file="internal/field-error.css" name=".field-error__icon" />

The prefix has the shared `visually-hidden` class, which Spinner uses too:

It's clipped to nothing (`clip-path: inset(50%)`) and taken out of the flow, so it takes no room and no gap. `display: none` or `visibility: hidden` would hide it from screen readers too. It's placed at the start of the error, which is `position: relative`, so it can never stick out past it.

The text is `--text-small`, in `--danger`, one of the status colors components may use because it carries meaning. The line is `--icon-md` tall, and the margin centers the smaller `--icon-sm` icon on that line.

Every control renders the error between its label (and description) and the control, as `docs/brand/forms.md` says: it's read before the control, and a phone keyboard or autofill menu can't cover it. A single checkbox or switch has its label beside it, so its error goes above the whole row, at its start.

### ReadOnlyNote: the "Read only" note

Every form control shows the same note beside its label when it's read-only: a lock and the words "Read only". It's how you can tell a field can't be changed before you try, in words rather than a fainter color, so nothing else about a read-only control changes. The control and its value stay at full contrast.

<Code file="internal/ReadOnlyNote.tsx" name="ReadOnlyNote" />

<Code file="internal/ReadOnlyNote.tsx" name="LockIcon" />

- **It's `aria-hidden`.** A screen reader already announces the control as read only, from `aria-readonly` or the native `readonly`, so hearing the note as well would say it twice. Being hidden also leaves it out of the control's name: the checkbox is still called "Joined in 2024", not "Joined in 2024 Read only". People who use voice control say the name they see first, so the note at the end doesn't get in their way.
- **It sits inside the label, after the label's text.** A checkbox or switch puts it in its `__label` span. A text field puts it in its `<label>`, and a group in its legend. An option in a read-only group doesn't show one, because the group's label already does, but an option that's read-only on its own in a group that isn't does.
- **Not when disabled.** A disabled control can't be changed either, and already says so by dimming, so it gets no note.
- **Not without a visible label.** A control named only by `aria-label`, such as a checkbox in a table row, has nowhere to put it.
- **The lock** is Lucide's lock, drawn here because Lucide is only a development dependency.

### Dev warnings

Some mistakes compile fine and still break something. For those, the components print a warning in the browser's console while you develop.

<Code file="internal/warn.ts" name="warn" />

- **Only in development.** A consumer's build tool replaces `process.env.NODE_ENV` with `"production"` in a production build, so the check is always true and the bundler drops the rest. Nothing is printed, and no warning text ships.
- **Once per message.** `shown` remembers every message printed, so a component that renders 100 times warns once.
- **One format.** Every message starts `[design-system] Checkbox:`, so you can tell where it came from.

A warning has to earn its place. One is added only when all three hold:

1. **TypeScript can't catch it.** If a type can make the mistake fail to compile, the type does it instead.
2. **The result is definitely broken**: wrong form data, a control with no accessible name, or a prop that silently does nothing. Never for unusual but valid use, or for style.
3. **Nothing else would show it.** The page doesn't visibly break, and the accessibility checks in Storybook don't catch it.

<Code file="internal/warn.ts" name="warnIfUnnamed" />

<Code file="internal/warn.ts" name="hasContent" />

`warnIfUnnamed` is the warning every form control and button calls. The props type already requires a label or an `aria-label`, but an empty string passes it, such as a label read from a content system that came back empty. `hasContent` checks whether label content would render anything: not empty, not only spaces, and not only `null`, `undefined`, or booleans. An `aria-labelledby` that points at another element's text counts as a name too.

    <tr><td>A <code>parent</code> box is in a group without <code>allValues</code></td><td>"Select all" ticks only itself.</td></tr>
    <tr><td>A <code>parent</code> box is outside a group</td><td>Same: there's nothing for it to select.</td></tr>
    <tr><td>An option in a group sets <code>name</code>, <code>invalid</code>, <code>error</code>, <code>required</code>, <code>checked</code>, <code>defaultChecked</code>, or <code>uncheckedValue</code></td><td>The group owns those, so the prop silently does nothing. One message lists every ignored prop and where to set it instead.</td></tr>
  </tbody>
</table>

They only warn about values that would have an effect. `invalid && …` is false for `invalid={false}`, which wouldn't change anything anyway, so it stays quiet. `checked !== undefined` does warn for `checked={false}`, because outside a group that would hold the box unticked.

The warnings are called during render, not in an effect, so they also show when a page is rendered on a server. In the unit tests, any test that leaves a warning behind fails, so a warning can't creep in unnoticed. A test that expects one takes it with `takeWarnings()` and checks the exact words.

### Joining class names

<Code file="internal/cx.ts" name="cx" />

`cx("checkbox", className)` gives `"checkbox"` when you pass no `className`, and `"checkbox mt-4"` when you pass `"mt-4"`. Your class goes on the wrapper, next to the component's own, which is why the `className` prop's JSDoc calls it "the place for layout classes such as margin".

## 4. How it looks

The look is in three files, all inside `@layer components`. Checkbox, Radio, and Switch work the same way, so most of it is shared: `internal/choice.css` has the row, the label, the control's edge and fill, the hit area, every state, the mark's motion, hot dog mode, and forced colors, and `internal/field.css` the description every form control shares. A fix there is a fix to all three. `checkbox.css` has only what's Checkbox's own. Each part carries a shared class next to its own, such as `class="choice__control checkbox__box"` on the box, and the shared files are imported first, so where they and `checkbox.css` set the same thing with equally specific selectors, Checkbox's own rule wins. Radio and Switch's pages point back here for the shared rules.

CSS layers set which styles win: the order is `theme, base, components, utilities`, so a Tailwind utility you add with `className` beats the component's own CSS for a one-off.

The CSS follows three conventions:

- **Classes name parts**: `.checkbox`, `.checkbox__row`, `.checkbox__box`, `.checkbox__indicator`, `.checkbox__mark`, `.checkbox__label`, `.checkbox__description`, and `.checkbox__error`. Most parts also carry the shared class for that part: `.choice`, `.choice__row`, `.choice__control`, `.choice__indicator`, `.choice__label`, `.field-description`, and `.field-error`. There are no modifier classes such as `.checkbox--checked`.
- **States come from ARIA attributes** where one exists: `aria-checked`, `aria-invalid`, and `aria-readonly`. A screen reader announces the same attributes, so what you see and what you hear can't disagree. Disabled is styled from Base UI's `data-disabled`, because Base UI puts it on the label as well as the box, so one attribute dims both.
- **Only semantic tokens.** A semantic token says what a value is for (`--border-strong`), not what it is (a gray). Every color token here points at the gray scale, never at a brand color, so the checkbox looks right next to any brand. The only exception is `--danger`, a status color that carries meaning.

### The wrapper and the label row

<Code file="internal/choice.css" name=".choice" />

The row is the click target, so its height matters. `--choice` is the box's size, 24px. `--choice-row` is how tall a row should be: 32px with a mouse, and 44px when a touch screen is present. The row's padding above and below is half the difference, `(--choice-row - --choice) / 2`: 4px with a mouse and 10px on touch. The label text's line height is `--choice`, so the first line of text is exactly as tall as the box and lines up with it. A long label wraps under itself, and the box stays beside its first line.

<Code file="internal/field.css" name=".field-label a" />

A link in the label, such as "I accept the terms and conditions", is `ink` and underlined, not the page's brand-colored `link`, because components stay neutral (`docs/brand/color.md`). The underline is what marks it as a link. The same goes for a link in any form control's label, description, or error. The [Link in label](?path=/story/components-checkbox--link-in-label) story checks the color is set, not inherited.

<Code file="internal/choice.css" name=".choice:not(:has(> .choice__row))" />

A checkbox with no visible label has no row. The same padding then goes on the wrapper, so it's still a full row tall.

### The box

<Code file="internal/choice.css" name=".choice__control" />

<Code file="components/Checkbox/checkbox.css" name=".checkbox__box" />

The shared rule makes every choice control a `--choice`-tall box with an edge and a fill, centered on the first line of its label. `checkbox.css` makes it square, with small rounded corners.

- **`--border-thick` in `--border-strong`.** A 2px edge that meets 3:1 contrast against the page in every theme. The fill changes with the state, but the edge always shows where the box is.
- **`--surface`** is the unticked fill, and **`--radius-sm`** rounds the corners.
- **`color: var(--on-action)`** is the mark's color, because the mark draws with `currentColor`. It's checked against the ticked fill, `--action`.
- **The transition** fades color changes and the hot dog press over `--duration-fast` (120ms).

### The hit area

<Code file="internal/choice.css" name=".choice__control::after" />

Every target must be at least `--target-min` in both directions: 24px with a mouse and 44px on touch. A labelled checkbox already is, because its whole row is the target. A checkbox with no label is only its 24px box. So the box gets an invisible `::after` that's `--target-min` square, centered on it. Clicks on it count as clicks on the box.

`inset` is how far it reaches past the box's inner edge, so a negative inset makes it bigger. The `::after` is positioned from inside the border, so the border width is taken off too. With a mouse, `(24 - 24) / 2 - 2` is `-2px`, which makes it the box's own 24px. On touch, `(24 - 44) / 2 - 2` is `-12px`, which makes it 44px.

Switch between mouse and touch to see it. The outlines are added by this demo only.

</Unstyled>

The wrapper of the second checkbox is as tall as its hit area. Without that, two unlabelled checkboxes stacked closely would overlap, and a tap meant for one would reach the other. Neither file has a media query for this: the tokens change with `data-pointer`, or by themselves when a touch screen is present, and the CSS reads them.

### Hover

<Code file="internal/choice.css" name='.choice__row:hover .choice__control:not([data-disabled], [aria-readonly="true"], [data-readonly])' />

Hovering anywhere on the row lightens the box to `--surface-hover`, so the whole row feels like one target. Disabled and read-only boxes are left out, so they don't look like they'd respond. A checkbox or switch says it's read-only with `aria-readonly`; a radio can't (ARIA gives read-only only to its group), so Base UI marks it `data-readonly`, and the shared rules leave out both.

A hover rule must never cover up a state. `:hover` adds specificity, so a hover rule usually beats a state rule. This one only changes the background, so an invalid box keeps its `--danger` edge while hovered.

### Focus

<Code file="internal/choice.css" name=".choice__control:focus-visible" />

`:focus-visible` matches when the browser decides focus should be shown: after the keyboard, but not after a mouse click. The ring is an `outline`, never only a `box-shadow`, because Windows Contrast themes remove box shadows but keep outlines. `--focus` meets 3:1 in every theme, and `--focus-width` grows from 2px to 3px when someone has asked their system for more contrast.

### Ticked, mixed, and invalid

<Code file="internal/choice.css" name='.choice__control[aria-checked="true"]' />

Ticked and mixed boxes fill with `--action`: near-black in light mode, and near-white in dark mode. The fill isn't what says "ticked": the mark is, so the state never relies on color.

<Code file="internal/choice.css" name='.choice__row:hover .choice__control[aria-checked="true"]:not([data-disabled], [aria-readonly="true"], [data-readonly])' />

A hovered ticked box uses `--action-hover`, so it still looks filled.

<Code file="internal/choice.css" name='.choice__control[aria-invalid="true"]' />

An invalid box's edge turns `--danger`. The error message's words and icon carry the meaning; the edge only points at which control it belongs to.

### Disabled and read-only

### The mark and its motion

<Code file="internal/choice.css" name=".choice__indicator" />

<Code file="internal/choice.css" name=".choice__indicator[data-starting-style]" />

<Code file="components/Checkbox/checkbox.css" name=".checkbox__mark" />

When a box is ticked, Base UI adds the indicator with `data-starting-style` for its first frame, then takes it off. The CSS transition runs from the starting style (invisible, and scaled to `--motion-scale`, 85%) to the normal style, so the mark pops in over `--duration-base` (200ms) with `--ease-bounce`, a curve that overshoots a little. Bounce is kept for toggles, chips, and success states.

When a box is unticked, Base UI adds `data-ending-style` and waits for the transition to finish before it removes the indicator. The rule after these in the file makes leaving quicker than arriving: `--duration-fast` with `--ease-in`, which starts slow and speeds up.

Only `opacity` and `transform` animate, which browsers can do smoothly. Under reduced motion, the tokens change instead of the CSS: `--motion-scale` becomes 1 and `--ease-bounce` becomes a plain ease-out, so the mark fades in without moving.

### Hot dog mode

<Code file="internal/choice.css" name='[data-theme="hotdog"] .choice__control' />

<Code file="internal/choice.css" name='[data-theme="hotdog"] .choice__row:active .choice__control:not([data-disabled], [aria-readonly="true"], [data-readonly])' />

In hot dog mode, `--shadow-sm` is a hard shadow offset 2px down and right. While you press the row or the box, the box moves 2px down and right and the shadow goes, so it looks pressed into its shadow. Disabled and read-only boxes don't press, since nothing happens when you click them.

### Windows Contrast themes

<Code file="internal/choice.css" name="@media (forced-colors: active)" />

<Code file="components/Checkbox/checkbox.css" name="@media (forced-colors: active)" />

Windows Contrast themes (forced colors) replace every color with a few system colors the person chose. The CSS can't pick colors there, but it can pick which system color goes where:

- The box is `Canvas` (the page color) with a `ButtonText` edge, and the mark is `HighlightText`.
- Ticked and mixed boxes fill with `Highlight`. The hover selectors are repeated here, because they're more specific than the plain ticked rule and would otherwise make a hovered ticked box `Canvas`, hiding the mark.
- The invalid edge goes back to `ButtonText`. The `--danger` rule would otherwise win, and forced colors can turn it into the page color, hiding the box.
- Disabled goes back to full opacity and shows with `GrayText` instead: a gray edge, a gray fill when ticked, and gray label text. Read-only was never dimmed.

## 5. Keyboard, screen readers, and forms

### Keyboard

### Screen readers

A screen reader learns everything from the box's attributes: it's a checkbox (`role`), what it's called (`aria-labelledby` or `aria-label`), whether it's ticked, unticked, or mixed (`aria-checked`), and whether it's required, invalid, read-only, or disabled. Then it reads the description and the error, from `aria-describedby`. The hidden input is `aria-hidden`, so it's never announced twice.

### Forms

The hidden input is a real `<input type="checkbox">`, so a form treats it like any native checkbox. Tick and untick these to see what the form would send:

<Unstyled>
  <SubmitDemo />
</Unstyled>

- **Ticked, with a `value`**: sends `name=value`.
- **Ticked, with no `value`**: sends `name=on`, the browser's default.
- **Unticked**: sends nothing at all, like a native checkbox. A server reads a missing name as "unticked".
- **Unticked, with an `uncheckedValue`**: sends `name=uncheckedValue`. Base UI adds a second, hidden input while the box is unticked, and removes it when it's ticked.
- **Disabled**: never sends, ticked or not, because the input is disabled. Read-only boxes do send.
- **Required and unticked**: the browser's own validation fails, because the hidden input has `required`. Most forms use `noValidate` and show the error with `invalid` and `error` instead, as in section 2.

Two props reach the hidden input for layouts that need them. `form` takes the id of a `<form>` elsewhere on the page, so a checkbox outside the form is still sent with it. `id` goes on the hidden input, not the box, so a `<label htmlFor>` elsewhere can tick it, but that label doesn't name it for screen readers. Use `children` or `aria-label` for the name.
