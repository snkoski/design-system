# How Number field works

A number field is a text field for amounts and quantities. Its value is a number, or `null` when it's empty. It reads what people type as they type it ("$1,234.5" is 1234.5), formats it when they leave the field ("$1,234.50"), and steps it with the arrow keys and two buttons, called steppers, at the end of the field. Around that, it's a text field like [Input](?path=/docs/components-input--how-it-works): the same label, help text, error, edge, states, and themes. This page covers what's different, and links to the Input page for the rest. Every code block is read from the source files when the page loads, so it's always the code that ships, and every demo is the real component.

[Base UI](https://base-ui.com), the unstyled library underneath, does the work: reading and formatting the number, the keyboard, the steppers, and the form. It comes in two sets of parts. `Field.Root`, `Field.Label`, `Field.Description`, and `Field.Error` (through `FieldError`) link the label, help text, and error to the input, as in every form control. `NumberField.Root`, `NumberField.Group`, `NumberField.Input`, `NumberField.Decrement`, and `NumberField.Increment` are the number field itself.

## From props to HTML

### The props

<Code file="components/NumberField/NumberField.tsx" name="Labelled" />

The same union as Input's: a `label`, or an `aria-label`, or the code doesn't compile.

<Code file="components/NumberField/NumberField.tsx" name="OwnProps" />

The value is a number. `onValueChange` gets a number on every keystroke that reads as one, on each step, and when the field is formatted on leaving it, and `null` when the field is emptied. `onValueCommitted` waits until a change is finished.

`smallStep` and `largeStep` change Base UI's defaults. Base UI's Alt step is 0.1 and its Shift step is 10, whatever `step` is: so Alt+Up turned 15 guests into 15.1, and in a salary field that steps by 1,000, Shift+Up added only 10. Here Alt steps by `step` and Shift by ten of them.

<Code file="components/NumberField/NumberField.tsx" name="NumberFieldProps" />

The rest of the props are the input's, from Base UI's `NumberField.Input`, minus some that would break a number field:

- `type` and `inputMode`, because the input must stay a text input, and Base UI picks the keyboard.
- `pattern`, `maxLength`, and `minLength`, because they'd check the formatted text: "$1,000" fails `pattern="[0-9]*"`, and the browser would stop the form. `min`, `max`, and `step` are the number's limits.
- `list` and `multiple`, which mean nothing for a number, and `size`, because ours is `md` or `lg`.
- `className`, which goes on the wrapper, as on every form control, and `children` and `render`.

### Props it drops

<Code file="components/NumberField/NumberField.tsx" name="dropped" />

<Code file="components/NumberField/NumberField.tsx" name="withoutDropped" />

TypeScript refuses all of these, but JavaScript can still pass them. Each would quietly do the wrong thing, so the component removes them before anything else. Three are Base UI props this component decides for itself:

- `allowWheelScrub` stays off: scrolling the page past a focused field must never change the number.
- `allowOutOfRange` stays on: a number typed outside `min` and `max` is kept as typed, so the page can say what's wrong, rather than being changed when you leave the field. The steppers and arrow keys still stop at the limits.
- `inputRef` is the component's own (below).

### The component

<Code file="components/NumberField/NumberField.tsx" name="NumberField" />

Reading it top to bottom:

1. **Pulling props apart.** The dropped props go first. Then the component's own props are taken out, with `size = "md"`, `step = 1`, `smallStep` defaulting to `step`, and `largeStep` to ten of them. Base UI rounds each stepped value, so a step of 0.07 takes Shift+Up to exactly 0.7.
2. **Warnings.** `warnIfUnnamed` catches an empty label, as in every form control. If `min` is greater than `max`, no number can be within both: Base UI would quietly turn every step, and every typed number on leaving the field, into `min`. Nothing on the page would look wrong, so this prints a development warning saying to swap them.
3. **`step` is only how far a press moves.** Base UI copies `step` onto the hidden input the form submits, as the browser's own `step`. With `min={0} step={1000}`, the browser would then refuse 85,500 and stop the form. So after every render, a layout effect sets the hidden input's `step` back to `"any"`. React only writes the attribute again when `step` changes, and the effect runs after that too. The steppers still move 85,500 to 86,500.
4. **The steppers** are left out when `steppers` is `false`, and always when the field is read-only, since they couldn't be used. `data-steppers` goes with them.
5. **The wrapper, label, description, and error**, as in Input. `name` and `disabled` go to both `Field.Root` and `NumberField.Root`, so the label dims and the hidden input is named.
6. **The field.** `NumberField.Root` gets the number props. `form` goes to the hidden input (through the root) and to the visible one, so pressing Enter in a field outside its form submits that form. Every other prop goes to `NumberField.Input`, where Base UI merges a page's `aria-describedby` with the field's own description and error.

## How it looks

The look is in two files, inside `@layer components`. The label, description, edge, hover, focus, invalid, disabled, read-only, hot dog, and forced colors rules are shared with Input in `internal/text-field.css` and `internal/field.css`: the input carries the shared class next to its own (`class="text-field__control number-field__control"`). [How Input works](?path=/docs/components-input--how-it-works) walks through each shared rule. `number-field.css` has only what's different.

### The field

<Code file="components/NumberField/number-field.css" name=".number-field" />

<Code file="components/NumberField/number-field.css" name='.number-field[data-size="lg"]' />

One custom property holds the field's height: `--control-md`, or `--control-lg` for large. Both follow touch screens (44px and 52px) and compact density (32px and 40px) with no rules of their own. The same property sets each stepper's width, so the steppers are always square.

<Code file="components/NumberField/number-field.css" name=".number-field__control" />

`tabular-nums` gives every digit the same width, so stepping 9 to 10 to 11 doesn't make the digits jiggle.

<Code file="components/NumberField/number-field.css" name=".number-field__box[data-steppers] .number-field__control" />

With steppers, the input's end padding is two field heights, so typed text stops where the first stepper begins.

### The steppers

<Code file="components/NumberField/number-field.css" name=".number-field__step" />

Each stepper is a square as tall as the field, over the input's end. Its hit area is the whole square, at least `--target-min` in every mode (24px with a mouse, 44px on touch), right up to the field's edge. `inset-inline-end` is a logical property: on a right-to-left page the steppers sit at the left. That's all NumberField's own CSS says about a stepper: how it's drawn is shared with DatePicker's calendar button and the calendar's month buttons, in `internal/inset-button.css`, and each stepper carries that file's class next to its own (`class="inset-button number-field__step"`).

<Code file="internal/inset-button.css" name=".inset-button" />

The button draws nothing itself: no fill and no border, so the field's edge shows through it. The rule resets the browser's own button look, for pages with no CSS reset.

<Code file="components/NumberField/number-field.css" name=".number-field__step:not(:last-child)" />

Decrease sits one square in from the end, beside Increase.

<Code file="internal/inset-button.css" name=".inset-button::before" />

Its visible box is a pseudo-element inset 4px (`--space-1`) on every side, with rounded corners. The field's edge is never thicker than 3px (hot dog's 2px border plus the 1px inset shadow of an invalid field), so the box never covers it, in any theme or state. Its transparent border is the stepper's border: invisible normally, and the outline that shows it in Windows high contrast.

<Code file="internal/inset-button.css" name='.inset-button:hover:not(:is([data-disabled], [aria-disabled="true"]))::before' />

<Code file="internal/inset-button.css" name='.inset-button:active:not(:is([data-disabled], [aria-disabled="true"]))::before' />

Hover fills the box with `surface-hover`, as a ghost button does, and pressing darkens it to `track-hover`. The fill fades over `--duration-fast`. Neither applies at a limit (`data-disabled`, which Base UI sets; the calendar's month buttons use `aria-disabled` instead, so the shared rules check both). Hovering a stepper doesn't darken the field's edge: the shared rule darkens it only when the input itself is hovered.

<Code file="internal/inset-button.css" name='.inset-button:is([data-disabled], [aria-disabled="true"]) .inset-button__icon' />

At a limit, or in a disabled field, the icon dims to 50%. The icon is `ink` on the field's `surface`: dimmed, that's 3.30:1 in light, 4.65:1 in dark, and 3.71:1 in hot dog, above the 3:1 an icon needs. `tokens/contrast.json` can't hold an opacity, so `pnpm check:contrast --probe ink:surface:3 --opacity 0.5 --page surface` checks it.

**Hot dog mode** adds nothing. The field keeps the shared ink edge and hard shadow, and the steppers don't press into it, as a button would: the shadow belongs to the whole field.

### Windows high contrast

<Code file="internal/inset-button.css" name="@media (forced-colors: active)" />

Windows replaces every background, so a hover fill would vanish. Instead, each stepper shows as an outlined box in the field's text color, gray when it can't be used, and in the highlight color while hovered or pressed. The hover rule comes after the disabled one and leaves disabled steppers out, so it can't cover them up.

## Keyboard, screen readers, and forms

**Keyboard.** The field is one Tab stop: the steppers are skipped.

<table>
  <thead>
    <tr><th>Key</th><th>What happens</th></tr>
  </thead>
  <tbody>
    <tr><td>Up and Down</td><td>Plus or minus <code>step</code>, stopping at <code>min</code> and <code>max</code></td></tr>
    <tr><td>Shift with Up or Down</td><td>Plus or minus <code>largeStep</code> (ten steps)</td></tr>
    <tr><td>Alt with Up or Down</td><td>Plus or minus <code>smallStep</code> (one step)</td></tr>
    <tr><td>Home and End</td><td>Jump to <code>min</code> and <code>max</code>, when they're set</td></tr>
    <tr><td>Enter</td><td>Submits the form, as in any text field</td></tr>
  </tbody>
</table>

Letters are refused. A minus sign is accepted even when `min` is 0, because a typed number outside the range is kept for the page to check.

**Pointer.** A press on a stepper steps the value, and holding it repeats. With a mouse it also focuses the input, so the arrow keys work next; on a touch screen it doesn't, so the phone's keyboard doesn't open and cover the page.

**Screen readers** announce the label as its name, "Number field", the value, then the description and any error. If it's `required`, `invalid`, or read-only, they say so too. On a touch screen, swiping forward from the field reaches "Decrease" and then "Increase".

**Forms.** What `FormData` gets, from the hidden input:
