# How Progress works

A progress bar shows a task that's under way and will finish, such as an upload: it fills as the task goes, or slides while it doesn't know how long. This page walks through the real code underneath it. Every code block is read from the source files when the page loads, so it's always the code that ships, and the demo is the real component.

Progress shares its look and most of its code with Meter, whose "How it works" page explains the shared parts in full: the label row, the track, the fill and how it slides into place, the sizes, hot dog mode, and forced colors. This page covers what's different.

## What it's made of

Progress is built on [Base UI](https://base-ui.com)'s Progress, which gives it the `progressbar` role, the value attributes, and three states. It announces itself the way Spinner does, with the same shared timing.

## How props become attributes

<Code file="components/Progress/Progress.tsx" name="ProgressProps" />

`value` can be `null`, which is how Base UI says "doesn't know how long". Anything else that isn't a finite number counts the same, as it does in Base UI, so the fill and the attributes always agree. Then there's no value to show and no position for the fill, and progress.css slides it instead.

The label is announced through the same hook as Spinner's: it reads `delay` once, so the CSS fade and the announcement agree, and fills the status region after the delay or 100ms, whichever is longer. The region holds the label from then on, so a new label (such as "Uploaded resume.pdf" when the task is done) is announced as well. The value isn't in the region, so its changes aren't announced: a screen reader would otherwise be interrupted at every step.

## The CSS, rule by rule

### When it doesn't know how long

The fill shrinks to 40% of the track and slides from just off the start edge to just off the end, over and over, once every 1.4 seconds. It always goes forwards, never back and forth, which would look like the task undoing itself. It moves only with `transform`, and its speed comes from `--duration-loop`, which slows down under reduced motion rather than stopping, like Spinner's turn and Skeleton's pulse: a frozen loading indicator looks broken. On a right-to-left page it slides from right to left.

### The delay

With a `delay`, the bar is invisible until the delay is over, then fades in. It's CSS, so it works before JavaScript runs too. The same delay holds back the announcement.

<Code file="components/Progress/progress.css" name=".progress[data-delayed]" />

### The hidden label

`hideLabel` puts the shared `.visually-hidden` class on the label and the value, so screen readers still have them but they take no room: the bar is just its track. The outer element is `position: relative`, which keeps them, and the status region, inside it.

<Code file="components/Progress/progress.css" name=".progress" />

### No touch, density, or focus rules

Nothing about a progress bar can be pressed or focused, so it has no hit area, no focus ring, and nothing that changes with a touch screen or compact density.

## How it's tested

The unit tests check the role, name, and description, the value attributes and words, the default percent, clamping, the three states, not knowing how long (no value, no English words, and a value that isn't a finite number), `hideLabel`, the announcement (empty first, then the label, a changed label, never a changed value), the delay, that the server's HTML has the name and value with the status region empty, that it hydrates without a mismatch, refs, the empty-label warning, and the props type. The stories check what needs real CSS: that each fill covers its value's share of the track, each size's height with a mouse and on touch, that a sliding fill starts off the start edge and moves toward the end (and the other way on a right-to-left page), that a hidden label takes no room, the colors in all three themes, and hot dog's edge.
