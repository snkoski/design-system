# How Rating works

A rating is a row of stars where someone gives one score, such as their interest in a job. Underneath, it's a radio group: each star is a radio, the group submits one number, and the keyboard is a radio group's. Read [RadioGroup's How it works page](?path=/docs/components-radio-group--how-it-works) first. This one covers what's different: the stars are made from a number, the stars up to the chosen one fill in, a Clear button empties it again, and hovering previews a choice.

## 2. The component

<Code file="components/Rating/Rating.tsx" name="Rating" />

In order, it:

- Checks it has a name, as every form control does, and that `max` is a whole number of 1 or more. A `max` that isn't falls back to 5 and prints a warning in development.
- Gets the value to show from `useResettableValue`, and passes it to Base UI's RadioGroup every time, never a `defaultValue`. That's what lets Clear empty it: a radio can't be unchecked, but a group given `null` shows none.
- Warns in development when the value isn't one of the stars (7 of 5, or 2.5): no star would show, and the form would send nothing.
- Calls `onValueChange` when a star is chosen, with Base UI's details. If the page cancels the change, an uncontrolled rating stays as it was.
- Shows Clear while there's a value and the rating isn't required, read-only, or disabled. Pressing it calls `onValueChange(null)`.
- Moves focus back to the stars when Clear disappears while it has focus, whether it was pressed or the page took it away. React sends no blur for an element it removes, so a ref set on focus still says Clear had it.

The star is Lucide's, twice: a filled shape underneath and the outline on top, so the outline (bold in hot dog) covers the fill's edge.

`onValueChange` gets a number, or `null` from Clear. A star's change passes Base UI's details as a second argument; a clear has none. There's no `size`: a star is a choice control's size (`--choice`, 24px), like a checkbox's box.

## 4. Following a form reset

<Code file="internal/useResettableValue.ts" name="useResettableValue" />

A form reset puts each hidden radio back as it was when the page loaded, but Base UI's state doesn't follow it: the stars kept showing the last choice while the form sent the first. So the hook listens for the form's `reset` event, waits for the browser to finish, puts an uncontrolled rating back to `defaultValue` (a controlled one keeps `value`), and sets the hidden radios to match what's shown. It reports no change: nobody chose anything. Building Rating found the same problem in RadioGroup and SegmentedControl, which use this hook too.

### The preview

While the pointer is on a star, the stars are drawn as choosing it would leave them. It's the one hover rule in the system that covers up a state, on purpose. It's off when the rating is read-only or disabled, and while a star has keyboard focus, so the arrow keys always show their own choice.

## 6. The color

The `color` prop is turned into what the wrapper renders by a helper Rating and RatingSlider share. A keyword (`"gold"`, the default, or `"brand"`, ignoring case and spaces) becomes `data-color`. Anything else is a CSS color, set inline as `--rating-color` and used as given in every theme, with `data-color="custom"`. In the browser it asks `CSS.supports` whether the value is a color, and warns in development if not; the CSS-wide keywords such as `inherit` warn too, since on a variable they reset it rather than color anything, and so does `transparent`, which hides the stars.

<Code file="internal/ratingColor.ts" name="ratingColor" />

The component's CSS sets `--rating-color` on the wrapper from the matching token: `rating-gold` (deep amber in light, bright gold in dark, ketchup in hot dog) or `rating-brand`. Both are checked for 3:1 against the page, cards, and tinted panels in every theme. An inline `--rating-color` beats both rules. Because the wrapper sets the variable itself, a parent can't: the prop is the way in, and a brand file changes `--rating-gold` or `--rating-brand` instead.
