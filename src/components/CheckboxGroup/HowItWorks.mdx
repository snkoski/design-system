# How Checkbox group works

A checkbox group is one question with several answers, any of which can be ticked: "Which services do you need?" It's one form field made of several checkboxes, and its value is the list of the ticked options' values.

Each option is a real `Checkbox`, so this page doesn't repeat how the box works. [How Checkbox works](?path=/docs/components-checkbox--how-it-works) covers the box, its CSS, the shared error message (`FieldError`), and the dev warnings. This page covers what the group adds: one label, description, and error for the whole question, one name for the form, and the link between the group and its options.

Every code block on this page is read from the real files when the page loads, so it's always the code that runs. Every demo is the real component.

`Fieldset.Root` would normally render a `<fieldset>`, but its `render` prop swaps that for Base UI's `CheckboxGroup`, a `<div role="group">`. So there's no native `<fieldset>` or `<legend>`. `role="group"` with `aria-labelledby` is the ARIA way of saying the same thing: these controls belong together, and this is their name.

### Required and invalid

A group has no `required` prop, because ARIA has no required state for a group. To ask for at least one choice, say "(required)" in the label, check the value when the form is sent, and set `invalid` and `error`. This demo does exactly that.

<Unstyled>
  <Inspect hint={<>Press "Request a quote" with nothing ticked. Then tick an option.</>}>
    <RequiredServices />
  </Inspect>
</Unstyled>

When the form is sent with nothing ticked, the demo sets `invalid` on the group. Base UI passes it from the group's `Field.Root` to everything inside:

- `data-invalid` on the wrapper, the group, and every option's wrapper, label, and box.
- `aria-invalid="true"` on every option's box and hidden input, so a screen reader announces each option as invalid.
- The error, between the description and the options, with an id. That id is added to the group's `aria-describedby` and to every option's. Someone who Tabs straight to an option still hears what's wrong.

Ticking an option clears `invalid`, and Base UI takes all of it off again. No single box is `required`, so the browser's own validation has nothing to check: checking the group is the page's job.

This is the whole pattern:

```tsx
const [value, setValue] = useState<string[]>([]);
const [sent, setSent] = useState(false);
const invalid = sent && value.length === 0;

<CheckboxGroup
  label="Services (required)"
  name="services"
  value={value}
  onValueChange={setValue}
  invalid={invalid}
  error="Choose at least one service."
>
  <Checkbox value="design">Design</Checkbox>
  <Checkbox value="development">Development</Checkbox>
</CheckboxGroup>
```

### Disabled and read-only

<Unstyled>
  <Inspect hint="Click the options, and press Tab. The read-only options take focus but can't change. The disabled ones can't take focus at all.">
    <div className="checkbox-demo__form">
    <CheckboxGroup label="Services" name="booked" disabled defaultValue={["design"]} description="Booking opens in May.">
      <Checkbox value="design">Design</Checkbox>
      <Checkbox value="development">Development</Checkbox>
    </CheckboxGroup>
    <CheckboxGroup label="Your plan" name="plan" readOnly defaultValue={["design"]} description="Chosen when you signed up.">
      <Checkbox value="design">Design</Checkbox>
      <Checkbox value="development">Development</Checkbox>
    </CheckboxGroup>
    </div>
  </Inspect>
</Unstyled>

- **Disabled** goes to the group's `Field.Root`, which disables every option. Each one gets what a disabled checkbox gets: `data-disabled`, `aria-disabled="true"`, `tabindex="-1"`, and a disabled hidden input, so the form doesn't send it. The group and its wrapper get `data-disabled` too.
- **Read-only** has no Base UI prop on the group. It travels through the group's context instead (section 3), and each option adds it to its own: `aria-readonly="true"` and `data-readonly` on every box. The group element itself gets nothing, because ARIA's read-only state belongs to the controls. The group's label gets a "Read only" note with a lock, hidden from screen readers, and the options don't repeat it. The shared `ReadOnlyNote` draws it, and [How Checkbox works](?path=/docs/components-checkbox--how-it-works) explains it.
- **The label and description stay at full strength** in both. Disabled dims only the options (section 4), and read-only dims nothing.

### Select all

<Unstyled>
  <Inspect hint={<>Click "All services" a few times. From the mix you made, it goes to all, then none, then back to your mix.</>}>
    <CheckboxGroup label="Services" name="services" allValues={["design", "development"]} defaultValue={["design"]}>
      <Checkbox parent>All services</Checkbox>
      <Checkbox value="design">Design</Checkbox>
      <Checkbox value="development">Development</Checkbox>
    </CheckboxGroup>
  </Inspect>
</Unstyled>

A `Checkbox` with `parent` is a "select all" box. Base UI's `CheckboxGroup` drives it with `allValues`, the values of every option:

- **Its state comes from the options.** It's `aria-checked="mixed"` when some are ticked, `"true"` when all are, and `"false"` when none are.
- **`aria-controls`** lists the ids of the boxes it controls, so assistive technology can tell what it affects.
- **`data-parent`** appears twice. Base UI puts it on the box. This code puts `data-parent="true"` on the option's wrapper, so the group's CSS can indent the other options under its label text.
- **Its hidden input has no name**, because Base UI leaves the name off a parent box. It never sends anything: it isn't an answer to the question.

### The component

<Code file="components/CheckboxGroup/CheckboxGroup.tsx" name="CheckboxGroup" />

It runs top to bottom on every render:

1. **Build the context.** `hasAllValues` is whether `allValues` was passed. `useMemo` keeps the same context object until `readOnly` or `hasAllValues` changes. Every option reads the context, and React re-renders all of them whenever its value is a new object, so a new object on every render would re-render every option for nothing.
2. **Warn if it has no name**, with the shared `warnIfUnnamed`.
3. **Make it one field.** `Field.Root` takes `name`, `disabled`, and `invalid`, and every option inside shares them.
4. **Make the group.** `Fieldset.Root` is rendered as `BaseCheckboxGroup`, which gets the rest of the props: `value`, `defaultValue`, `onValueChange`, `allValues`, and anything else, such as `data-testid`. `ref` goes there too, so it reaches the element with `role="group"`.
5. **The label**, only when there is one. With only an `aria-label`, there's no legend, and `aria-label` names the group directly.
6. **The description, the error, and the options.** The error comes after the description and before the options, inside the group, and shows while `invalid` is true. The options sit inside the context provider, so every `Checkbox` among them knows it's in a group.

`readOnly` isn't a prop of Base UI's `CheckboxGroup`, so it goes through the context: each option reads it and becomes read-only itself.

### What the group tells its options

<Code file="components/CheckboxGroup/context.ts" name="CheckboxGroupContextValue" />

<Code file="components/CheckboxGroup/context.ts" name="CheckboxGroupContext" />

React context is a value a component provides that any component inside it can read, however deep, without passing props through every level. Its default is `null`, so a `Checkbox` outside a group reads `null`, and one inside reads this object. Its presence is how a checkbox knows it's an option.

In a group, a `Checkbox` changes in four ways. [How Checkbox works](?path=/docs/components-checkbox--how-it-works) shows the code.

- **It renders `Field.Item`, not `Field.Root`.** Base UI links each control to the nearest field around it. If an option rendered its own `Field.Root`, that would be its nearest field, and it would get its name and validity from there instead of from the group.
- **The group's value decides what's ticked.** The option's own `checked`, `defaultChecked`, and `uncheckedValue` are ignored.
- **The group owns the field's props.** The option's own `name`, `invalid`, `error`, and `required` are ignored. A dev warning names any you set, and where to set them instead.
- **It needs a `value`.** That's what identifies it in the group's value, and what the form sends. Without one, a dev warning says so.

An option keeps its own `disabled`, `readOnly`, `description`, and `onCheckedChange`. Disabling one option, such as one that's fully booked, leaves the rest working.

## 4. How it looks

Most of the group's look is shared with RadioGroup and SegmentedControl: `internal/choice-group.css` has the wrapper, the group, and the stack of options, and `internal/field.css` the label and description. Each part carries a shared class next to its own, such as `class="choice-group__group checkbox-group__group"`. `checkbox-group.css` has only what this group adds. Each option is a `Checkbox`, drawn by `checkbox.css` and `internal/choice.css`. Like every component's CSS, it's in `@layer components`, and it uses only semantic tokens.

The options stack with no gap. Each option's row is already `--choice-row` tall (32px with a mouse, 44px on touch), so the rows touch, and every point between two boxes belongs to one of them.

<Code file="components/CheckboxGroup/checkbox-group.css" name=".checkbox-group__options:has(> .checkbox[data-parent]) > .checkbox:not([data-parent])" />

With a "select all" box, the other options move in by `--choice` plus `--space-3`, the width of a box and its gap. Their boxes line up under the parent's label text, which shows they belong to it. `:has()` checks whether the options contain a parent box, using the `data-parent` its wrapper carries.

**Disabled dims only the options.** `internal/choice.css` dims each disabled option, and the group's label and description stay at full strength. They often say why the choices can't be changed ("Booking opens in May."), so they must stay readable. There's a testing reason too: Storybook runs axe, an accessibility checker, on every story. axe skips the contrast check on a disabled control's own label, but not on a group's legend, so a dimmed legend would fail. Read-only dims nothing: the note beside the label is its cue.

## 5. Keyboard, screen readers, and forms

### Keyboard

<table>
  <thead>
    <tr><th>Key</th><th>What it does</th></tr>
  </thead>
  <tbody>
    <tr><td>Tab and Shift+Tab</td><td>Move from option to option. Every option is its own Tab stop, and disabled ones are skipped.</td></tr>
    <tr><td>Space</td><td>Ticks or unticks the focused option.</td></tr>
    <tr><td>Enter</td><td>Doesn't tick. Inside a form with a submit button, it sends the form, like Enter on a native checkbox.</td></tr>
    <tr><td>Arrow keys, Home, and End</td><td>Do nothing.</td></tr>
  </tbody>
</table>

This is the difference from a [Radio group](?path=/docs/components-radio-group--how-it-works), which is one Tab stop with arrow keys to move between its radios. Radios are one choice, so moving between them changes the answer. Checkboxes are independent, so each one is a stop of its own.

### Screen readers

Moving into the group, a screen reader can announce the group and its name from `role="group"` and `aria-labelledby`. On each option, it reads the option's name and state, then its `aria-describedby`: the group's description, the option's own description, and the error while there is one.

### Forms

<Unstyled>
  <ServicesForm />
</Unstyled>

- **Each ticked option sends `name=value`**, all under the group's one name. Two ticked options send the name twice. On a server, or with `formData.getAll(name)`, that's a list.
- **They're sent in page order**, not in the order they were ticked.
- **Nothing ticked sends nothing.** There's no empty entry, so a server should read a missing name as an empty list.
- **Disabled options never send**, ticked or not, and nor does anything in a disabled group. Read-only options do send.
- **The "select all" box never sends**, because it has no name.
