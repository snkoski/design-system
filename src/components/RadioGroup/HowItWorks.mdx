# How RadioGroup and Radio work

A radio group asks one question and offers a few answers, of which exactly one can be chosen. It's two components. `RadioGroup` is the question: its label, help text, error, and which answer is chosen. `Radio` is one answer: a circle, a dot when it's chosen, and its words. [SegmentedControl](?path=/docs/components-segmented-control--how-it-works) is the same group drawn as connected buttons, and its page builds on this one.

### One Tab stop

A radio group is a single stop when you press Tab. Only one option at a time has `tabindex="0"`, which puts it in the Tab order. The others have `tabindex="-1"`, which lets them take focus but leaves them out of the Tab order. This is called a **roving tab index**, because the 0 moves to whichever option is current:

- With an option chosen, it's the chosen one.
- With nothing chosen, it's the first option that isn't disabled. (In the demo, that's Free before you choose anything.)

Inside the group, the arrow keys move focus, wrapping from the last option to the first, and skipping disabled ones. Moving also chooses. Base UI does this in two steps: the group notes that an arrow key was pressed, and then the option that receives focus clicks its own hidden input. Focus arriving by Tab doesn't choose anything, so tabbing into a group with nothing chosen leaves it that way until you press Space or an arrow key.

### The hidden input

Next to every radio, Base UI renders an `<input type="radio">`. It's there for forms: the browser only submits and validates real inputs, so this is what a `<form>` sends and what `required` checks. Base UI keeps it in step with the radio and gives it the group's `name`, the option's `value`, and the `disabled`, `required`, `readonly`, and `form` the group has. It's hidden three ways:

- An inline style shrinks it to a 1px clipped box, so you can't see it. (The demo leaves inline styles out.)
- `tabindex="-1"` keeps it out of the Tab order: the span is what you focus.
- `aria-hidden="true"` hides it from screen readers, so each option is only announced once.

A click on the circle or its label reaches this input, and Base UI listens for the input's change. So choosing always goes through the browser's own radio behavior.

There's one thing in the demo's HTML that can mislead: the `checked` attribute on a hidden input only shows how it started. Once you choose something, React updates the input's `checked` property, which HTML doesn't show, and leaves the attribute where it was. The property is what the form reads, as the form demo in section 5 shows.

### Why `null` means nothing chosen

To control the group, you hold its value in your own state and pass `value` and `onValueChange`. A group with nothing chosen yet needs a value that means "nothing", and that's `null`, not `undefined`. React's rule, which Base UI follows, is that a component whose `value` is `undefined` controls itself: Base UI decides once, on the first render, whether `value` is `undefined`, and stays that way. So clearing a controlled group by setting `value={undefined}` wouldn't clear it: Base UI would print an error about switching from controlled to uncontrolled, and go back to showing its own remembered value. `null` keeps the group controlled and chooses nothing. The form demo in section 5 has a button that sets it back to `null`.

## 2. From props to HTML

### The group

<Code file="components/RadioGroup/RadioGroup.tsx" name="RadioGroup" />

From the top:

- **The name check.** `warnIfUnnamed()` prints a warning while you develop if the group would have no name, for example a label that came back empty from a CMS. [Checkbox's How it works page](?path=/docs/components-checkbox--how-it-works) explains it, and every form control's warnings.
- **`Field.Root` gets `name`, `disabled`, and `invalid`.** Base UI's RadioGroup reads all three from the field, and the field passes `disabled` and `invalid` on to the parts inside it: each `Field.Item`, label, and radio. That's why one prop marks everything in the state table above. `className` goes here too, joined to `radio-group` by `cx()`, so the layout classes you pass land on the outer wrapper.
- **`Fieldset.Root` renders the group.** Base UI's `render` prop replaces a part's element with the one you give it, and merges their props. Here the fieldset's element is replaced by Base UI's RadioGroup, so one `<div>` is both the fieldset (named by its legend) and the radio group (with its value and keyboard handling). The fieldset's children (the legend, description, error, and options) go inside it.
- **Everything else goes to Base UI's RadioGroup.** `{...rest}` passes on `value`, `defaultValue`, `required`, `readOnly`, `form`, `aria-label`, and any other attribute. `ref` reaches the element with the radiogroup role.
- **`<string | null>`** tells TypeScript the group's value is a string or `null` (see "Why `null` means nothing chosen"). Base UI's `onValueChange` could, by its type, pass `null`. A person choosing never does, so the wrapper only calls your `onValueChange` with a string. Your handler's type says so: it gets a `string`, never `null`.
- **The label only renders when there is one.** With `aria-label` and no `label`, there's no legend, and the group is named by `aria-label` instead.
- **The error only renders when there's an `error`,** and `FieldError` only shows it while `invalid` is true (`match={invalid}`). So you can pass the message all the time and switch `invalid` on and off.

### The group's props

<Code file="components/RadioGroup/RadioGroup.tsx" name="RadioGroupProps" />

The props are three types joined with `&`:

- **`Labelled`**, which makes sure the group has a name (below).
- **`OwnProps`**, every prop RadioGroup documents itself, with a comment that Storybook shows in the props table. Most are Base UI's, declared again here because Storybook's props table leaves out props inherited from packages in `node_modules`. It's in the whole file at the end of this page.
- **Base UI's RadioGroup props, minus some.** `className` (Base UI's can be a function; this one is a string), `render` (RadioGroup uses it itself), `aria-label` (`Labelled` owns it), and `inputRef` (a ref to one hidden input; Radio has its own), and every prop `OwnProps` declares again. Everything left, such as `onBlur` or `data-*` attributes, passes through.

An **accessible name** is what a screen reader says a control is called. The props type won't compile without one:

<Code file="components/RadioGroup/RadioGroup.tsx" name="Labelled" />

It's a union: the props must match one of the two shapes. Either there's a `label` and `aria-label` is optional, or there's no `label` and `aria-label` is a required string. `label` is typed `Exclude<ReactNode, undefined | null | boolean>`: anything React can render, except the values that render nothing. Plain `ReactNode` includes `undefined`, so `label={maybeLabel}` would compile even when there's nothing in it. ### One option

<Code file="components/RadioGroup/Radio.tsx" name="Radio" />

- **The circle** is Base UI's `Radio.Root` with `Radio.Indicator` and the dot inside. `{...rest}` gives it `value`, `id`, `ref`, `inputRef`, `aria-label`, and any other attribute. Base UI puts `id` and `inputRef` on the hidden input and `ref` on the span.
- **With label text**, the circle and the words go inside `Field.Label`, so the whole row is a label and clicking anywhere on it chooses the option. **With no label text**, the circle is rendered alone, and `aria-label` names it. Then there's no `<label>` element at all.
- **`Field.Item` gets `disabled`**, not `Radio.Root`. Base UI's Radio counts itself disabled if its field item is, and the item marks the label row with `data-disabled` too, which the CSS uses to dim the words.

Why every option needs a `Field.Item`: Base UI's field links a label to a control by giving the control an id, and giving the label that id in its `for`. One `Field.Root` holds one set of ids. The group is one field, so without an item of its own, every option's hidden input would get the field's one id, every label's `for` would point at the same input, and the options would share their descriptions. `Field.Item` starts a fresh set of ids for each option, while still passing on the group's description and error. That's why a radio's `aria-describedby` lists the group's description first, then its own.

The props leave out what the group owns. `required` and `readOnly` are set on the RadioGroup, and so are `name` and `invalid`, which Base UI's Radio never had. So `<Radio required>` doesn't compile, rather than compiling and doing nothing. A Radio only works inside a RadioGroup, so it doesn't need to find out whether it's in one. Used on its own, it still compiles, and it visibly does nothing, so you notice straight away. `disabled` is the one state an option can have by itself: one plan can be sold out.

`render` and `nativeButton` are left out too, so the radio is always Base UI's `<span>`. That's on purpose: a native `<button>` can't take focus while it's disabled, and Base UI always makes the chosen radio the group's Tab stop. A chosen, disabled button would hide the whole group from Tab.

## 3. How it looks

The look is in four stylesheets, all inside `@layer components`. Most of it is shared, so a fix there is a fix to every control that uses it: `internal/choice-group.css` has the group and its stack of options, `internal/choice.css` each radio's row, edge, fill, states, hit area, hot dog mode, and forced colors (the same rules as Checkbox and Switch, explained in full on [How Checkbox works](?path=/docs/components-checkbox--how-it-works)), and `internal/field.css` the label and descriptions. Each part carries a shared class next to its own, such as `class="choice__control radio__circle"`. `radio-group.css` has only what's the radio's own, and it's imported after the shared files, so it wins where they set the same thing. The design system's layer order is `theme, base, components, utilities`, so a Tailwind utility in your markup wins over the component's own CSS. Every value is a **token**, a named design value defined once in `tokens/tokens.json`. The CSS uses semantic tokens, which say what a value is for (`--action`), never primitives, which say what it is (`--gray-900`). Each theme points the semantic tokens at different colors, so the radio changes with the theme without rules of its own. They're all neutral grays, black, and white: brand colors belong to the layout around components.

### Hover, without covering up a state

<Code file="internal/choice.css" name='.choice__row:hover .choice__control:not([data-disabled], [aria-readonly="true"], [data-readonly])' />

<Code file="internal/choice.css" name='.choice__row:hover .choice__control[aria-checked="true"]:not([data-disabled], [aria-readonly="true"], [data-readonly])' />

Hovering anywhere on the row lightens an empty circle to `--surface-hover`, and darkens a chosen one to `--action-hover`. A disabled or read-only circle doesn't change, because you can't choose it. ARIA has no read-only state for a single radio, so Base UI marks it `data-readonly`; the shared rules leave out both that and a checkbox's or switch's `aria-readonly`. Hover only changes the fill, never the edge, so it can't hide the red edge of an invalid radio.

The second rule is more specific than the first: `[aria-checked="true"]` adds one attribute, so for a chosen circle it wins and keeps the dark fill. **Specificity** is how CSS picks between two rules that set the same property: the selector with more ids, classes, attributes, and pseudo-classes wins, and `:not()` counts what's inside it.

- **Invalid** turns the edge `--danger`. The error message above the options says what's wrong in words.
- **Read only** shows the plain cursor and doesn't dim: the circles and their words stay at full strength, because read-only content must stay readable. The cue is the "Read only" note beside the group's label.
- **Disabled** shows the "not allowed" cursor, and dims the circle and its words to 50%.

Disabled doesn't dim the group's label or description. axe, the accessibility checker every story runs, skips the contrast check on a disabled control's own label, but not on a group's legend, so a dimmed legend would fail it.

### The hit areas

A **hit area** is everywhere a click or tap counts. Every hit area in the system is at least `--target-min` in both directions: 24px with a mouse, and 44px when the device has a touch screen. A radio has two:

- **With words**, the whole row is the label, and it's `--choice-row` tall: 32px with a mouse, 44px on touch.
- **With no words**, the circle is alone, and 24px is too small on touch. So the circle gets an invisible `::after` box, centered on it, `--target-min` square. A pseudo-element is part of its element, so clicking it is clicking the circle.

<Code file="internal/choice.css" name=".choice__control::after" />

Its insets are measured from inside the circle's 2px edge, where its 20px padding box starts. On touch, `(24 − 44) / 2 − 2` is −12px, and a negative inset reaches outwards, so the box is 20 + 24 = 44px. With a mouse, it's −2px, and the box is 24px.

The wrapper of a radio with no words is padded to `--choice-row` too. Without that, stacked radios would be only 24px apart, and their 44px hit areas would overlap on touch, each taking some of the next one's taps:

<Code file="internal/choice.css" name=".choice:not(:has(> .choice__row))" />

Switch between a mouse and touch to see them. The dashed lines are the hit areas, and the sizes are measured from the page:

  <RadioHitAreas />
</Unstyled>

The tokens switch to their touch sizes when any touch input is present, or inside `data-pointer="coarse"`, which is how the demo shows touch on any device. The CSS never checks the pointer itself: it only reads tokens.

### Hot dog mode

Hot dog is the joke theme, in ketchup and mustard. Its controls get a hard offset shadow, and press into it when clicked:

<Code file="internal/choice.css" name='[data-theme="hotdog"] .choice__control' />

<Code file="internal/choice.css" name='[data-theme="hotdog"] .choice__row:active .choice__control:not([data-disabled], [aria-readonly="true"], [data-readonly])' />

`--shadow-sm` is a solid shadow 2px right and 2px down in hot dog. Pressing moves the circle 2px right and down and takes the shadow away, so the circle lands where its shadow was. Disabled and read-only circles don't press. The press isn't built from a motion token, so it still happens with reduced motion: it's feedback that you pressed, not decoration.

### Forced colors

Windows' Contrast themes replace every color with a few system colors the person chose, and remove shadows. This is called **forced colors**.

<Code file="internal/choice.css" name="@media (forced-colors: active)" />

<Code file="components/RadioGroup/radio-group.css" name="@media (forced-colors: active)" />

- **The circle** gets a `ButtonText` edge on `Canvas`, the page color, and the dot `HighlightText`.
- **The invalid edge** goes back to `ButtonText`. The invalid rule is more specific than the circle's, so it would otherwise keep `--danger`, which forced colors redraws in the page color, hiding the circle.
- **A chosen circle** fills with `Highlight`, the system's color for selected things. The hover rules are repeated in this block: they're more specific than the plain chosen rule, so without them a hovered chosen circle would take the hover fill, which forced colors turns into `Canvas`, and the dot would vanish.
- **Disabled** goes back to full opacity, because dimming the system's colors could make them unreadable, and uses `GrayText` instead, the system's color for disabled things.

To see it without Windows, open Chrome's DevTools, open the Rendering panel, and set "Emulate CSS media feature forced-colors" to "active".

## 4. Keyboard and screen readers

<table>
  <thead>
    <tr><th>Key</th><th>What it does</th></tr>
  </thead>
  <tbody>
    <tr><td>Tab, Shift+Tab</td><td>Moves focus into the group, to the chosen option, or the first option that isn't disabled if nothing is chosen. The next Tab leaves the group.</td></tr>
    <tr><td>Down arrow, Right arrow</td><td>Moves to the next option and chooses it. From the last option, it wraps to the first. Disabled options are skipped.</td></tr>
    <tr><td>Up arrow, Left arrow</td><td>Moves to the previous option and chooses it, wrapping from the first to the last.</td></tr>
    <tr><td>Space</td><td>Chooses the focused option. You need it when you've tabbed into a group with nothing chosen.</td></tr>
    <tr><td>Enter</td><td>Nothing. Base UI stops it, because a radio is chosen with Space. It doesn't submit the form either.</td></tr>
    <tr><td>Home, End</td><td>Nothing. Base UI turns them off for radio groups.</td></tr>
  </tbody>
</table>

In a read-only group, the arrow keys move focus without choosing, and Space does nothing. In a disabled group, Tab can still reach the chosen option, and nothing else works.

As you enter the group, a screen reader announces its name, from the legend through `aria-labelledby`, and its description and error, through `aria-describedby`. On each option it reads the option's name, that it's a radio button, whether it's checked (`aria-checked`), and the descriptions and error linked to it. `aria-required`, `aria-invalid`, and `aria-disabled` let it say, in its own words, that the group is required, invalid, or unavailable. Say "(required)" in the label too, so everyone sees it, not only screen reader users.

## 5. In a form

A form sends the hidden inputs: the chosen one's `value`, under the group's `name`. Try each switch, and clear the choice:

<Unstyled>
  <RadioGroupForm />
</Unstyled>

- **Chosen:** `FormData` has one entry, such as `plan = "team"`.
- **Nothing chosen:** no entry at all, not an empty one. On the server, the field is missing.
- **Disabled:** no entry, even with something chosen, because a disabled input is never submitted.
- **Read only:** the chosen value is sent. Read-only blocks changes, not submitting.
- **Required with nothing chosen:** the browser's own validation would stop the form submitting, because `required` is on every hidden input. The demo's form has `noValidate`, which turns that off, as a form that shows its own errors does: it checks the value on submit and sets `invalid` and `error` ([the Required story](?path=/story/components-radio-group--required) shows how). `required` still puts `aria-required` on the group.
- **`form`:** a group outside its `<form>` can still submit with it. Pass the form's `id` as `form`, and Base UI puts it on every hidden input.
